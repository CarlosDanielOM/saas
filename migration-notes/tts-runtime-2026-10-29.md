# Native TTS runtime factory — 2026-10-29

## Status and scope

This wave adds an application-owned Rust TTS runtime factory over the provider and Fish catalog implementations already present in `dimabot/src/server/services/tts/`. It closes the local factory/configuration gap for those services: the factory reads environment values at the source-equivalent point, supplies speech paths, dispatches Piper/Fish/Kokoro, and exposes Fish catalog lookup/search. It does not migrate or adopt the TypeScript application callers, and it does not close the broader TTS dependency graph.

The runtime reuses the existing `PiperTtsService`, `FishTtsService`, `KokoroTtsService`, and `FishCatalog`; it adds no second provider implementation. A single `reqwest::Client` is shared by the runtime and its catalog, while cloned catalog handles share the existing `Arc`-backed cache. Provider services still use their current config and protocol code. The shared `Environment` alias is now re-exported by `runtime`; optional `with_environment` hooks on Fish, Piper, and the catalog preserve their explicit config APIs for existing callers.

`TtsRuntimeConfig` supplies an explicit speech root and configurable provider/catalog templates. `speech_root_from_module_dir` derives the source's lexical `path.resolve(module directory, '../../routes/public/speech')` result from an absolute UTF-8 Linux module directory supplied by the application. The factory does not guess a runtime location from `CARGO_MANIFEST_DIR`. The real process adapter reads `var_os` and converts invalid OS bytes lossily, matching Node's replacement-character behavior.

Construction does not read TTS environment values, create output directories, spawn a provider, or send provider requests. Constructing the default HTTP client can still load native TLS and proxy configuration; therefore construction is not claimed to be free of all environment access or I/O.

## Source-compatible read points and behavior

- Runtime construction creates one catalog using the runtime's shared HTTP client and environment adapter. Provider selection defaults to Piper when absent or unresolved, matching the queue registry contract; explicit Piper, Fish, and Kokoro values select their existing native service implementations.
- Fish synthesis reads `FISH_AUDIO_API_KEY` for an attempt after the primary provider failure, so a changed key is visible to the fallback. Catalog lookup reads that key only on cache miss; a valid cache hit returns before reading it. Runtime clones use the same catalog/cache instance.
- Piper reads `PIPER_HTTP_URL` at its existing source decision point. The source truthiness distinction is preserved: `"///"` enters the CLI branch after slash trimming, while `" ///"` is truthy and enters HTTP. No URL whitespace trim was added beyond the existing blank-value test and trailing-slash rule. `PIPER_DATA_DIR` is trimmed and used only by the CLI branch; `PIPER_PYTHON_BIN` is read only on that branch and used when nonempty, otherwise `python3` is selected. `PUBLIC_API_URL` and, when that value is missing/blank, `NODE_ENV` are read after successful public audio output is written. Private output and failed synthesis skip these public-URL reads. A configured nonblank public URL short-circuits the `NODE_ENV` read.
- Speech paths preserve Node lexical joining and URL construction. Runtime and configuration debug output redact speech roots, endpoints, credentials, and provider environment configuration while retaining safe timeout/cache metadata.
- Test templates can override endpoints, deadlines, response bounds, and cache settings without changing production defaults. Existing explicit provider configuration constructors remain available.

The malformed Piper URL parity check confirms the branch, environment read order, and error category. Node and Rust transport wording is not expected to be identical. The owned-process environment probe confirms the concrete adapter's lossy conversion for an invalid OS byte; it does not mutate the parent process environment.

- `tests/fixtures/tts_runtime_reference.mjs` evaluates AST-selected Piper getters, the actual `getDirname` implementation, and Node's actual `path.resolve` for 13 configuration/environment cases and five module-directory contexts.
- `tests/fixtures/tts_runtime_dynamic_reference.mjs` evaluates the actual TypeScript provider/catalog/deadline/tag/voice modules in an isolated VM with an ordinary environment-read proxy. Seven scenarios cover Fish primary-failure fallback and single-provider success, Kokoro success and missing key, Piper CLI and HTTP routing, and catalog cache-hit/miss credential timing.
- Native ignored replays compare actual runtime wires, authorization, model/body fields, SDK key/message packing, public URLs, environment-read order, cache results, and an owned real CLI shim. The dynamic TypeScript oracle mocks fixture-only filesystem, spawn, fetch, and synthetic Fish SDK behavior; neither it nor the native fixture calls a real provider, engine, external Fish SDK transport, Twitch API, or cdom201 service. Prior concrete provider/SDK coverage was retained and fresh native regression fixtures were replayed.
- A local HTTP fixture verified one keep-alive TCP connection across eight sequential requests spanning Piper, Kokoro, Fish success, Fish single-attempt failure, Fish fallback, and catalog get/search. This proves scoped same-origin connection reuse under the fixture; it does not imply a single connection across the different production origins.

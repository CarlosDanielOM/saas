**Status as of 2026-10-23:** final source-backed library validation passed for the six opt-in utility features. The six modules are independently gated by `chat-message`, `timer-policy`, `credit-policy`, `cron-queue`, `credential-crypto`, and `twitch-tokens`. Credit date inputs are `JsDate` values in epoch milliseconds. The caller owns parsing strings and constructing dates, including JavaScript `Date.parse` behavior; invalid dates are represented explicitly. The policy keeps millisecond precision and JavaScript TimeClip/ISO formatting semantics for the value it receives. This boundary avoids silently substituting Rust RFC3339 parsing for JavaScript date parsing. The credit-policy feature alone enables `serde_json/float_roundtrip`; strict binary64 parsing and a TTS bit-level numeric regression preserve the source's extreme-value result without epsilon or relaxed comparisons.

`parse_cron_queue_job` returns `Result<Option<CronQueueJob>, CronQueueParseError>`. Invalid JSON syntax within the configured bound, or valid JSON without a usable job name, returns `Ok(None)` to retain the TypeScript parser's invalid-payload behavior. More than 127 nested object/array containers returns `Err(CronQueueParseError::DepthLimitExceeded { maximum_depth: 127 })`; this explicit depth budget is a resource boundary. Consumers must handle that error visibly and must not silently discard it as an ordinary invalid payload. JSON serialization aims at the same structure and field omission rules; property ordering and number spelling are not a byte-parity contract. JavaScript values without JSON equivalents (for example functions, cyclic objects, non-finite JSON numbers, and lone UTF-16 surrogates) are outside the API.

Queue reuse is intentionally narrow. Follow ledger and stream memory destructively use `BLPOP` from the left and `RPUSH` to requeue; unsupported jobs are pushed to the dead-letter list before their dedupe marker is cleared. Stream memory and clips share attempt normalization/increment rules, but each caller still decides retryability, attempt ceilings, future-due handling, delay, and cleanup. Clips additionally use `BLMOVE` to a processing list and fence ack/requeue/recovery/dead-letter changes with an owner lease. The generic helpers do not define that lease protocol, and a clip migration must port its full raw-payload identity and lease-loss behavior separately.

## Token storage compatibility and migration boundary

The Mongo adapter targets the existing `users.accounts` Twitch entry and retains the stored `{iv, content}` credential envelope. The Redis adapter reuses existing account hashes, app-token key, bot-token mirror, streamer list, and refresh-lock key shapes. Constructors take already-created Mongo/Redis handles and explicit cipher, OAuth, and clock dependencies; they do not connect, read process environment, or initialize production state. OAuth HTTP calls reuse the existing Twitch client and its transient retry policy.

Several deliberate concurrency/safety differences are part of the Rust source contract and need review before wiring any caller:

- Mongo save and revoke fence writes against the encrypted refresh-token snapshot captured by the read, bind platform and account id in the same array element, and never upsert a missing account. On compare loss, lifecycle code rereads authoritative state before deciding whether a rotated token can be reused or revocation repaired; it does not overwrite a newer snapshot.
- Redis token publication compares the full expected credential snapshot; cold hydration requires credential fields to remain absent. Refresh-lock release is an atomic owner-checked compare/delete. Revocation atomically checks the account snapshot before clearing its credentials and any older bot mirror, preserving a concurrent newer account publication. Bot-mirror publication separately checks that the supplied access token still matches the current account token, so a delayed stale write cannot restore a revoked or replaced token.
- Cache publication writes credential fields without manufacturing an `id` marker in a partial hash. It preserves metadata already in the hash and invalidates the aggregate account-list cache only at the source-compatible transition. This keeps TypeScript's full-account hydrator boundary visible.
- A valid authoritative stored access token can hydrate a cold credential hash. Hydration uses the stored expiry with the stored token, rather than borrowing an expiry from a potentially stale cache entry.
- OAuth success followed by Mongo persistence failure is returned as a persistence error; the unpersisted token is never returned for use. Cache failure after persistence is separately reported so a retry can hydrate the persisted rotation. App-token expiry must be positive, finite, integral, and representable as a JS safe integer before Redis `EX` publication.
- Streamer auth checks account permissions; bot auth follows the existing bot path and does not introduce that pre-refresh permission gate. `up_to_date_permissions` is stored but is not used as an additional gate.

An independent source review (round two) found no remaining source blocker in the reviewed token paths, including snapshot fences, rereads after compare loss, revocation repair, the atomic bot-mirror guard, missing-user handling, and monotonic refresh-wait timing. This is source-review evidence only; it does not establish runtime or adapter verification. These compare-and-set writes are not implemented by current TypeScript writers. In particular, the TypeScript refresh lease is five seconds and may expire during an OAuth request, and TypeScript writers do not participate in Rust's compare-and-set conditions. Do not enable Rust storage writers alongside TypeScript writers without a caller-by-caller mixed-writer review. This foundation does not install refresh-all, worker, logger, or debug-cache paths.

### Waits and pacing retained in source

| Wait | Reason and scope |
|---|---|
| Queue consumers use blocking `BLPOP` with their configured five-second idle timeout. | Waits for future queue work without a hot polling loop. The primitive accepts a timeout but does not choose a consumer's queue policy. |
| Follow-ledger requeues on a channel-lock conflict and sleeps 1.5 seconds before retrying. | Avoids immediately reacquiring a known-busy channel in a tight loop. This is consumer policy, not part of `cron_queue`'s shared transport helpers. |
| Stream-memory consumers retain configured requeue delay (default 2.5 seconds), one-second error backoff in the queue loop, and configured worker-lock retry (default 10 seconds). | Requeue delay spaces retries for future-due jobs, channel-lock contention, and failed work. The one-second sleep follows a queue-loop exception to avoid a hot error loop. Worker-lock retry waits for exclusive ownership. These waits belong to the worker and are not implied by the Rust queue module. |
| Token refresh retries retain 400 ms then 900 ms backoff for network failures and HTTP 5xx responses only. | Backoff separates transient OAuth retries; permanent failures, other HTTP statuses, and 429 are not retried by this policy. The shared Twitch OAuth implementation owns its configured retry behavior. |
| A token refresh waiter polls every 150 ms for at most 4.5 seconds while another owner may be refreshing under a five-second lock TTL. | Gives the lock holder time to publish a usable token and stops early when the lock disappears. This is coordination, not arbitrary pacing; the final in-flight store operation can overshoot the deadline. |

The pure policy modules have no sleeps. No worker scheduling behavior changed as part of this batch; no TypeScript queue consumer or worker is replaced by adding these features. Any later consumer migration must separately review the source's polling, retry, lease, and future-due waits against that consumer's implementation.

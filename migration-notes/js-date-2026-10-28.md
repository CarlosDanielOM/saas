# JavaScript Date.parse compatibility — 2026-10-28

## Scope and status

This wave adds an opt-in Rust `js-date` utility for the Date.parse grammar used by the standalone interaction reducer and its domain-event time adapter. It closes the legacy parser gap for this local feature. It does not establish parity for every date-consuming TypeScript feature, complete all Date consumers, or advance the dependency-complete migration to 100%. The wider migration remains incomplete; 14 TypeScript files are archived and unchanged in this wave. No TypeScript source was retired, and there was no caller or live cutover.

`js-date` is independently selectable and uses the existing `libc` dependency; it is not enabled by default or coupled to TTS or worker profiles. The `domain-events` feature selects it for `domain_events/time.rs` and `overlays/interaction-model.rs`. `serde_json` was added as a dev dependency for the standalone fixture tests; no crate version or lockfile change was made.

## Implementation and boundaries

`utils/js_date` ports the pinned V8 scanner, ISO and legacy date grammar, component composition, timezone offsets, TimeClip handling, NUL termination, and UTF-16 code-unit behavior. It exposes Rust string and UTF-16 entrypoints. The standalone reducer now applies this parser when comparing timestamps across interaction IDs and for same-ID event ordering; the domain-event adapter selects the same implementation. The V8-derived code is accompanied by its BSD license in `utils/js_date/LICENSE.v8`.

The local-wall-time adapter currently targets Linux libc and configured system zoneinfo. It samples 17 points at six-hour steps across the surrounding interval, assumes offsets do not exceed 24 hours and that an offset regime around the target lasts at least six hours, and follows V8's ICU choices: a gap uses the former offset and an overlap selects the earliest matching instant. This supports ordinary IANA transitions represented by the host zone data, including historical second offsets and 24-hour skips. Arbitrary custom TZ files with shorter regimes or offsets beyond 24 hours are unsupported. Its `OnceLock` fast path is used only when `TZ` is exactly `UTC` on first conversion; it assumes that process timezone stays fixed and that `UTC` has its conventional zero offset. All other zones use libc's normal conversion and sampling path. The adapter's OS zoneinfo must match the pinned Node runtime's ICU data for exact parity; timezone database versions, names, historical data, and future rule differences can change results. The existing runtime Dockerfile does not explicitly install `tzdata`, so deployment readiness and parity in that image have not been established. Unsupported platforms and libc conversion failures return no parsed value.

This adapter does not close date parsing/casting in Mongoose, HTTP `Retry-After` diagnostics, emotecatalog, or other TypeScript consumers. Those paths remain open for source/caller reconciliation.

## Behavior evidence

The initial isolated parity run compared 261 generated inputs against pinned Node in five fresh timezone processes: UTC, America/New_York, Europe/Berlin, Australia/Lord_Howe, and Pacific/Apia. The corpus includes ISO and legacy forms, historical local mean time, far years, timezone gaps and overlaps, UTF-16 surrogates, and embedded NUL. All 261 inputs matched in each zone. A separate 236-case domain-contract corpus passed. The offline TypeScript oracle used Node 24.22.1, V8 13.6.233.17-node.58, ICU 78.3, and tzdata 2026e. Its seeded fake `Math.random` is injected only into allowlisted oracle modules; the process-global `Math` is unchanged, and repeated goldens were byte-identical.

A negative control restored only the pre-change `domain_events/time.rs` and `overlays/interaction-model.rs` from HEAD `f1c82306`, then ran the expanded source corpus. It failed the expected `reduce/date-other-id/legacy-older` case: the prior implementation retained an older state where the oracle returns `null`. This confirms the corpus detects the behavior gap without changing unrelated source files.

Final compile/lint/runtime receipts and raw evidence are in the [evidence pack](evidence/2026-10-28-js-date/README.md). The initial UTC candidate's median of seven samples, after a 10,000-iteration warmup, measured microseconds per operation over 100,000 operations per sample:

| Workload | Node | Rust before UTC fast path |
|---|---:|---:|
| ISO | 0.154412 | 0.465472 |
| Legacy | 0.157712 | 1.945191 |
| Invalid | 0.116994 | 0.124535 |
| Mixed | 0.163004 | 1.052298 |

The Rust measurement includes the public UTF-16 API and checksum/valid-count work; Node used prepared strings with the same cases and checksum work. The first result exposed libc timezone-call overhead; an explicit-UTC fast path and a keyword lookup optimization followed. The [final comparison](evidence/2026-10-28-js-date/js-date-comparison.json) matched checksums and valid/invalid counts:

| Workload | Node (µs/op) | Rust (µs/op) | Rust / Node |
|---|---:|---:|---:|
| ISO | 0.15153045 | 0.17096845 | 1.1283× (12.83% slower) |

The mixed result is small and is not a statistical claim. Only UTC was benchmarked after the fast path, so there is no performance conclusion for other zones. These are synthetic measurements, with no production throughput, CPU, or memory claim. The [evidence README](evidence/2026-10-28-js-date/README.md) records test totals, caps, limitations, and raw sample links.

No production resources were used or changed, and nothing was deployed or pushed. Evidence collection and build checks followed the migration resource limits: 6 CPUs, 4 GiB memory with no swap, 256 PIDs, two build jobs, and an 8 GiB Cargo cache ceiling. Production identity remained unchanged.

# Lane F2: keyword cooldown and ingress oracle (authoring only)

No execution lease was available. The tests and fixture below are authored but have not been compiled, generated, or run. No service call has been made by this lane.

The ignored Redis test requires `AST_INGRESS_TEST_REDIS_URI` on loopback and creates one UUID-qualified channel key. It calls Redis `SET key 1 NX PX 200` directly, checks contention and bounded expiry, and deletes only that key after collecting results. If a command or connection fails before cleanup, the key retains its short TTL. This is a real Redis network check when run, but it does **not** call `NativeCommandStore::acquire`: constructing that adapter requires its unrelated application collaborators. Static inspection shows that method uses the same SET arguments and maps `Option<String>::is_some()`. The public production key helper is used by the test and command path; the test asserts its literal output. The production cooldown calculation helper is exercised in process for pro, premium, free and absent plans, for both keyword and ordinary command cases. Neither helper assertion tests the application adapter over the network.

The ignored Twitch test creates a one-request loopback server per case, joins its thread after the request, and uses `TwitchChatSender` and the injected app-token adapter. It intends to check success, 401 mapping, POST path without a query, authorization and the complete plain chat JSON body. The endpoint's actual body includes `broadcaster_id`, `sender_id`, `message`, and `for_source_only`; it is not just the message field. Its compilation and network behavior remain unverified.

The fixture is generated by an integration runner using `--write` and supplied to `AST_KEYWORD_ORACLE`; Rust does not invoke Node. The source fixture substitutes a recorder for `executeCustomCommand`, so it observes the body handed off, name, argument and authorization before the real command gates, and it substitutes delivery. The existing ignored Rust oracle assertion is still only a hardcoded fixture sanity check: **a serialized native-versus-source comparison has not been implemented**. In particular, `AstBodyParser` sees the parser context after gates, not the `CommandReference` authorization or every source handoff, and the source error case is injected at a different seam. An explicit ingress handoff observer (or a comparable test seam) is needed to capture these without inventing authorization from test inputs; the integration team should implement and verify that comparison. The malformed variants have been added to the source fixture and native in-process test but are not yet compared to each other.

Static source inspection identifies these schema-guarded deviations: a truthy non-boolean `enabled` reaches the source recorder but the native ingress rejects it; missing `cmd` causes source `normalizeKeyword(undefined)` to throw while the native ingress skips it. The schema declares `enabled` boolean and `cmd` string; malformed persisted documents are outside that contract. The source recorder does not execute the real command body, so missing/non-string `message` cannot be assessed at the parser boundary from that oracle alone. The native parser receives an empty string for either; the source command uses `message || ''`, which preserves a truthy non-string value. The schema declares message as string with an empty default. Missing message is a valid legacy/default case and both command paths select an empty string, subject to verification with the real command seam.

The source uses `start` when settings or mode are absent/null; unknown non-null modes follow its anywhere branch. Native ingress makes the same selection, and `keyword_matches` implements the corresponding enum modes. The current unknown-mode fixture uses a message starting with the keyword, so it does not distinguish start from anywhere; a non-starting matching message and corresponding index fixture are still needed.

The TypeScript cooldown utility specified in the task, `src/utils/command_cooldown.ts`, is absent in this checkout; the live command handler and native policy were read instead. No deployment, commit, build, test, formatter, Node, Docker or service-backed execution was performed.

## Lead integration (2026-10-31, team3 lead — MiniMax M3.1 Flash)

The lane reported the native-vs-source comparison as incomplete and handed the
missing seam to the integration team. That seam is now implemented.

### The handoff seam

`CommandStore` gained one **default-implemented** method:

```rust
fn handoff(&mut self, _request: &CommandReference, _body: &JsonValue) {}
```

`execute_command_body` calls it as its first statement — before the `enabled`,
permission, cooldown and count gates. That is exactly where the TypeScript
calls `executeCustomCommand`, which is the seam the source fixture replaces, so
an observer now sees the same four facts the source's recorder sees: the body,
the command name, the argument and the authorization. A production store pays
nothing for it: the default implementation does nothing.

The lane's diagnosis was right that the parser seam cannot supply this: it
receives its context *after* the gates and does not expose the authorization.
The `CommandReference` does, so the seam belongs on the store.

### The comparison is now native-vs-source, not native-vs-hardcoded

`native_observations()` serializes the native ingress into the source fixture's
document shape — `{schema, cases: {<scenario>: {bodies, executions, delivered}}}` —
and `native_observations_match_the_actual_source_oracle` compares it field by
field against the generated oracle. The comparison covers the three observable
channels and asserts that both sides saw the same set of scenarios. The
hardcoded fixture check is kept, but it now only validates the **fixture's**
shape; it is no longer presented as a native-behaviour check.

### Malformed-body parity

* **`enabled` is now judged by JavaScript truthiness.** The source writes
  `if (!keyword.enabled)`, so `"yes"` is truthy and the source still runs the
  command. The native used `as_bool().unwrap_or(false)`, which skipped it. The
  new `js_truthy` helper in `runtime/command.rs` reproduces JavaScript's rules
  and is used by both the ingress gate and the command body's `enabled` gate.
  This changes nothing for a schema-valid boolean and restores parity for a
  malformed one.
* **A missing `cmd` is a deliberate, pinned divergence.** The source calls
  `normalizeKeyword(undefined)` and throws out of `handleKeywords`. The native
  skips the malformed keyword and continues. The comparison asserts the source
  throws and the native does not, and that both request the same bodies and
  deliver nothing. The schema declares `cmd` as a string, so this only differs
  for a malformed document, and copying a crash into the native would abort the
  whole keyword loop.
* **A discriminating match-mode scenario was added.** The previous
  `unknown_mode` case used a message that starts with the keyword, so it could
  not tell `start` from `anywhere`. `unknown_mode_anywhere` uses an `anywhere`
  index and the message `say hello there`, with the body's own mode still
  `unknown`. Only a port that maps an unknown mode to `anywhere` — as the
  source's `keywordMatches` does — proceeds, so the case now fails a port that
  falls back to `start`. The native maps an unknown mode to `anywhere`, so it
  matches the source.
* **A parser-boundary nuance the oracle cannot observe.** The source fixture
  replaces `executeCustomCommand`, so the real body is never parsed: a missing
  or non-string `message` cannot be assessed at the parser boundary from that
  oracle. The native passes `""` for both, which the source's
  `cmdDB.command.message || ''` also produces for a missing message, but a
  non-string message would reach the source's parser as `42`. Pinning that
  needs a fixture that runs the real command module.

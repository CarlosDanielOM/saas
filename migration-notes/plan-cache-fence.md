# Plan-cache fence utility

Reviewed on 2026-10-27.

Status: accepted as an opt-in, library-only Rust utility after final-source quality/parity checks and disposable Dragonfly verification. It is not wired into TypeScript callers or worker profiles and was not deployed. The shared logger's existing acceptance remains unchanged; both utilities are available and independent.

## Source and dependency boundary

The utility is [`dima-rust/src/utils/plan_cache_fence.rs`](../dima-rust/src/utils/plan_cache_fence.rs), gated by Cargo feature `plan-cache=["redis"]`. It ports exactly three Lua scripts from [`dimabot/src/utils/plan_cache_fence.ts`](../dimabot/src/utils/plan_cache_fence.ts) and two from [`dimabot/src/domain_events/polar_billing_events.ts`](../dimabot/src/domain_events/polar_billing_events.ts). TypeScript remains the domain-event and billing owner. Rust depends on the caller-supplied Redis `ConnectionManager`; there is no Polar HTTP, MongoDB, or logging dependency. The billing context key is passed opaquely by the caller, preserving the existing TypeScript hash/key construction without copying billing-hash logic.

## API and protocol contract

`PlanCacheFence::new(connection)` is lazy and defaults each operation to a two-second cooperative deadline. `with_deadline` accepts a positive per-operation deadline and does not change the injected connection's global timeout. The adapter owns immutable prepared `redis::Script` handles, safely handles a confirmed `NOSCRIPT`, and does not retry ambiguous mutations. A mutation timeout or transport failure may mean the write happened; callers must reconcile before retrying. The checks validated deadline configuration and typed unknown-outcome errors, but did not inject a stalled transport to test deadline expiry.

Methods: `write_account`, `check_accounts`, `accept_credits`, `invalidate_plan`, `sync_credits`, `read_account`, and `read_accounts`. Helpers expose JavaScript-compatible version formatting and the existing key shapes. Preserve persistent plan/snapshot fences, empty legacy versions, equal-version acceptance, Lua byte ordering, raw JSON byte comparison, both exhaustion-key variants, and `Keep` semantics. `write_account` ignores any caller-supplied reserved `__polar_plan_version` and appends its internal version; `AccountSnapshot::public_fields()` strips that field. `invalidate_plan` retains the source's entire-account-hash invalidation. The billing context key is caller-supplied.

The version formatter accepts integer milliseconds within the JavaScript `Date` range, including negative values with JavaScript `padStart` behavior. Invalid dates return `InvalidDate` rather than formatting `NaN`; missing date or missing/empty key retains the source's empty-version behavior before date validation.

`read_account` runs one atomic `HLEN`/`HGETALL`/fence script, bounds size before returning fields, and rejects a cached `id` that differs from the requested ID with `Protocol`. `read_accounts` returns results in request order from a bounded pipeline of independently atomic per-account reads; the batch itself is not one atomic snapshot. A confirmed `NOSCRIPT` may reload and retry this read-only pipeline once; other failures are not retried. Aggregate version validation and optional raw-JSON publication remain a single atomic `check_accounts` call; never split this into chunks, since that would break the final all-account fence check. Redis Lua atomicity does not roll back writes issued before a later script runtime error, and the adapter does not mutation-retry such ambiguous outcomes.

Limits are per request: ID 1,024 bytes; value 1 MiB; request 4 MiB; at most 256 account fields; aggregate validation at most 4,096 accounts; each read account at most 256 fields and 64 KiB; read batches at most 64 accounts and 64 KiB of read-batch arguments. Oversized accounts return `AccountTooLarge`; oversized inputs return `InputTooLarge`. These bounds do not add key enumeration or unbounded scans.

This protocol establishes plan freshness only. It does not hydrate MongoDB, reconcile account-list membership, prove credential freshness, or implement credential CAS. Existing compatible whole-hash `HSET` and full-hash invalidation behavior remain and can affect credentials. Caller adoption remains outside this utility port; credential-sensitive adoption requires an integration review covering ownership/CAS and all mixed writers.

## Verification evidence and limits

Final source receipt reports that 175 Rust build/test source and test hashes matched the checkout. Capped quality completed successfully: formatting; checks for no features, `plan-cache`, and `plan-cache,logger-redis`; Clippy for both feature profiles; 21 standalone library tests (including Redis foundation tests); and 38 combined plan-cache/logger regression tests. Source parity passed in both profiles, comparing five exact Lua bodies, 66 version cases, and five key cases. Separate explicit doctest runs passed two doctests each; these repeated runs are not unique test counts. One initial Clippy `collapsible_if` warning was corrected mechanically by the lead before the final successful run.

The disposable Dragonfly fixture passed 135 original-source `EVAL` versus Rust-method scenarios, covering legacy/missing/empty/equal/newer versions, exact raw JSON and TTL, flag staleness, mixed TypeScript/Rust writer protection, 16 actual concurrent old-write/new-invalidation races, atomic read states, field/byte bounds, and wrong-ID `Protocol` handling. `SCRIPT FLUSH` recovery passed for all five methods and the read-only pipeline. A 64-account read batch passed and 65 was rejected. Aggregate validation accepted 4,096 accounts in one `EVALSHA`; a stale final row rejected publication while preserving the current aggregate, and 4,097 was rejected before Redis execution. Eight warm writes used eight `EVALSHA` and zero full-body `EVAL` calls; this is command-path evidence, not a latency or bandwidth benchmark.

The capped run completed in 94.718 seconds with a warm cache; this is not a speed benchmark. Limits were 6 CPU, 4 GiB memory and memory-swap (no swap), 256 PIDs, two Cargo jobs, and an 8 GiB private cache (peak 673,845,248 bytes). Minimum available memory was 12,177,752,064 bytes, above the 4 GiB reserve. All 19 production container identities/images/start times/restart counts/statuses remained unchanged; no task-owned containers or networks remained, and no task images were created. Four deployed worker dependency graphs were identical. Receipts and logs are retained under `/root/.local/state/rust-plan-cache-20261027-h_5e14s2/artifacts/`.

The source intentionally rejects invalid JavaScript dates rather than returning `NaN`; wrong cached account IDs fail with `Protocol`. These are explicit corruption/invalid-input behaviors. No stalled-transport fault injection was performed, so the two-second cooperative deadline's actual expiry path is not runtime-verified. Do not infer production gains, deployment readiness, or live caller compatibility. No production service, data, caller, or worker profile was in scope.

## Host limits and cleanup

The production-host checks followed [`dima-rust/AGENTS.md`](../dima-rust/AGENTS.md): 6 CPU, 4 GiB memory and memory-swap (no swap), 256 PIDs, two Cargo jobs, and an 8 GiB private Cargo cache, preserving the 4 GiB production reserve. Task-owned source snapshots, baseline copies, compiler targets, and Cargo caches were removed; receipts, logs, the source-hash manifest, and the validation runner were retained. This library-only acceptance does not authorize building/deploying cron or touching live services.

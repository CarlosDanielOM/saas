## Production-host Rust build and test policy

This checkout is on the production VPS. Before Rust validation, inspect CPU, memory, disk, and production load. The user authorized up to 6 GiB for the compiler. The default is 6 GiB and requires at least 14 GiB `MemAvailable` before startup; if host headroom is lower, `scripts/saas-ops build cron --rust-memory-gib 4` explicitly selects the supported 4 GiB cap and requires at least 12 GiB before startup. Either cap requires at least 8 GiB `MemAvailable` during execution. On 2026-10-21, the host had about 13.8 GiB available, so the current combined candidate uses the explicit 4 GiB option. The helper option and its operations tests verify the strict 4/6 choices, default 6 GiB, cron-only restriction, and selected resource limits. Combined candidate `cron-240af282cb85` has now compiled at 4 GiB in 176.782 seconds with a warm cache hit; details and limits are recorded in [`migration-notes/follow-defense-baseline.md`](../migration-notes/follow-defense-baseline.md), with no speedup claim. Use one task-owned Docker compiler container across the parent and delegates, with `--cpus=6`, memory and memory-swap both equal to the selected cap (no swap), `--pids-limit=256`, and `CARGO_BUILD_JOBS=2`. The 6 GiB cap has compiled successfully: candidate `cron-d33c17d71dd8` took 186.583 seconds with a cache hit, and formatting, checks, Clippy, tests, and release-binary dry runs passed for both feature profiles. Its digest and baseline-only runtime evidence are recorded in [`migration-notes/follow-defense-baseline.md`](../migration-notes/follow-defense-baseline.md); that candidate was cleaned up without deployment after stream-health telemetry joined scope. This establishes compilation at 6 GiB, not a speedup versus prior builds. The combined 4 GiB compiler result is recorded in the same migration note. Apply the selected limit to dependency builds, build scripts, linkers, and generated test or fixture binaries. Stop if available memory falls below the 8 GiB floor or production service pressure rises; these are operational thresholds, not a peak-memory forecast or reservation, and CPU/memory caps do not eliminate I/O impact. Preserve existing CPU-load and disk-space checks. Use a read-only source snapshot or copy and task-owned Cargo target/cache capped at 8 GiB; do not mount `.env` files or production data, expose the Docker socket, or use host networking. Dependency downloads may need network access, but tests use isolated disposable fixtures only. The `--rust-memory-gib` option is cron-only and accepts 4 or 6; other targets reject it. The option and its operations tests are verified, and combined candidate `cron-240af282cb85` completed Rust compilation at the 4 GiB cap and passed all three worker runtime suites; its bounded production acceptance watch passed. Do not raise the 6 GiB ceiling, remove hard caps, or fall back to host execution. `nice`/`ionice` may supplement but do not replace cgroup limits. On a non-production development machine, Cargo may run locally with `CARGO_BUILD_JOBS=1`.

The previous stream-activity validation ran Cargo compilation and Rust test/benchmark binaries directly on the host with `CARGO_BUILD_JOBS=2` and `nice -n 10`; only its MongoDB fixture was in a container limited to 1 CPU and 768 MiB. The Cargo job count and `nice` setting are not hard host limits and do not meet this policy. The `saas-ops build cron` path now compiles in a capped task-owned toolchain container and verifies its applied limits; the deployed cron release was built and validated through this path.

The cron build compiles three binaries sequentially in one capped compiler. Stream activity and raid analytics use `--no-default-features --features mongo`; the baseline projector uses `--no-default-features --features mongo,redis`. Cargo defaults intentionally retain the complete shared foundation (`mongo`, `redis`, `postgres`, `http`). The `postgres` feature is optional SQLx/PostgreSQL support for a possible future telemetry port; current telemetry stays in the TypeScript cron host. `http` is optional Axum support, and `redis` is the optional Dragonfly-compatible client. The two dependency profiles have separate graph guards and receipts; SQLx/Axum are excluded from all three workers, while Redis is limited to the baseline worker. Use `scripts/saas-ops build cron --rust-feature-matrix` only for an explicit feature-transition audit. The helper stores dependencies and Cargo artifacts in a private persistent cache at `~/.local/state/saas-ops-rust-cache/v1`, keyed by toolchain image, manifest, lockfile, recipe, features, and profiles. It enforces an 8 GiB cache limit, validates ownership markers, and rejects symlinked paths. Each run explicitly rebuilds all three worker release binaries while retaining dependency artifacts; the stream fixture example is not part of routine cron builds. The compiler is pinned to Rust 1.99.1 on Alpine/musl using the already validated immutable image `rust@sha256:557a94c82b485a14b569120e00867267108c734efe33f10cc31ca0cd5dd1eca9`; the toolchain pin must not change to an unvalidated image. Cache reuse reduces compile work only; it does not imply proportional runtime memory or CPU savings.

## Library conventions

Cargo features keep capabilities independent. The default feature set retains the complete foundation for library/manual consumers: `mongo`, `redis`, `postgres`, and `http`. MongoDB-only workers and their binaries are built with `--no-default-features --features mongo`; SQLx/PostgreSQL, Axum, and Redis are optional and excluded from that worker graph. `dotenvy` is part of the MongoDB feature for explicit environment-file loading. Map BSON documents into explicit structs with Serde, and call Garde `validate()` for additional field or business constraints. Future ports must preserve existing collection names, field types, defaults, and indexes. See [`README.md`](README.md) for the shared MongoDB, Redis, and dotenv foundation.

`dima_rust::utils::mongo::get_mongo_client().await` returns `mongodb::error::Result<&'static Client>`. It reads `MONGO_URI` from the process environment on first use without loading dotenv files, pings `admin` before caching the client in a Tokio `OnceCell`, and leaves failed initialization retryable. Use it within the application's long-lived Tokio runtime and share it across tasks and threads. Static storage does not keep the originating runtime alive; do not reuse the cached client after that runtime or the client has been shut down. Clone the native handle when needed; clones share the same pool. Callers select the database explicitly. The URI's default database may be used through driver behavior, but the utility adds no implicit fallback.

`dima_rust::utils::redis::get_redis_client().await` returns `redis::RedisResult<redis::aio::ConnectionManager>`. It reads `DRAGONFLY_HOST` and `DRAGONFLY_PORT` from the process environment, matching `dimabot/src/utils/databases/dragonfly.database.ts`, without loading dotenv files. It uses plain TCP with database 0 and adds no URI, password, TLS, or database-selection configuration. A Tokio `OnceCell` caches the manager only after the first connection and `PING` succeed; failed or cancelled initialization can be retried. The five-second bound applies to this initial connection and ping. The cached manager is an owned, cheap clone that shares a multiplexed TCP socket. Its response timeout is unset to preserve blocking command semantics; blocking commands and Pub/Sub should use separate dedicated connections when implemented. Use it within the application's long-lived Tokio runtime; static storage does not keep that runtime alive, and the cached manager must not be reused after runtime shutdown. The driver reconnects after an I/O disconnect, while a command that encounters the disconnect is returned to its caller and is not replayed. Configuration errors omit raw environment values. This utility does not load dotenv files; an executable must load explicitly selected files before creating the Tokio runtime.

# Downstream Queue Durability and Dragonfly Recovery

**Status: deployed to cron and API, production-checked, and task cleanup complete.** This change adds durable recovery for selected post-stream and clip-analysis queues. It does not make every cron queue durable, and it does not replay uncertain external effects.

The changed runtime paths are the cron analytics, maintenance, queue-consumer and clip-completion reconciliation code, plus the API [clip-recommendations route](../dimabot/src/server/routes/clip-recommendations.route.ts) and startup/snapshot analytics path in [stream analytics](../dimabot/src/utils/stream_analytics.ts). A source call trace found no bot runtime caller for these offline/online/snapshot queue producers; bot command analytics and the follow-ledger branch are unchanged. The bot retains its current production image and is not a target for this release.

## Scope and reused sources

The existing `stream_offline` path already records step receipts on the stream session, and automatic clip recommendations already persist their analysis, billing, notification, and preview-cleanup state in `ClipRecommendation`. The remaining gap was accepted queue work stored only in Dragonfly: loss of its Redis list could lose a not-yet-started summary, maintenance, or clip-analysis job even when the stream-session receipt or permanent acceptance marker still existed.

The change reuses the existing `enqueueCronJob` producer, `stream_memory` and `clip_recommendations` workers, the `ClipRecommendation` completion reconciler, and the stream-session step receipts. It adds `cron_job_intent` as the durable record for pending jobs. Scope is limited to `stream-memory-summary`, weekly/monthly stream-memory maintenance, and `clip-recommendation-analysis`; unrelated cron queues remain Redis-only. This adds no stream-metric or accounting-ledger mutation and does not change clip billing identity.

## Queue intent and recovery behavior

`enqueueCronJob` writes a canonical payload and intent to Mongo before publishing to the Dragonfly list. The intent has a permanent job identity, queue key, due time, next-publication time, dedupe/automatic-acceptance identity, and status (`queued`, `processing`, `completed`, `dead`, `uncertain`, or `legacy_accepted`). The collection has no TTL: terminal rows preserve dedupe and outcome evidence. New automatic stream-offline jobs keep a durable Mongo acceptance identity keyed by job, channel, and session.

Both selected workers run bounded intent recovery at startup and periodically. Each pass examines at most 100 eligible Mongo intents; republishing is rate-limited by `nextPublishAt` (30 seconds). Before publishing, one Redis Lua operation uses `LPOS` over at most 1,000 queue entries to avoid adding a payload that is already present and restores the automatic acceptance marker when applicable. If a payload is deeper than that bounded scan, a duplicate queue copy is possible; the Mongo claim prevents two copies from both acquiring the job. While the intent is `queued`, its Mongo payload is the source of truth, so the worker can republish pending work after Dragonfly loses the queue list or marker.

When a worker removes a payload from Redis, it claims the Mongo intent with an owner, unique token, and five-minute lease. Renewals and state transitions require the same owner/token and an unexpired lease. Workers check claim ownership around processing. A completed, dead, or uncertain intent is terminal. An expired `processing` lease is changed to `uncertain`, never automatically requeued: an external AI, email, or other effect may have succeeded before the worker lost its acknowledgement. Memory workflow exceptions after work starts also become uncertain. This is durable pending-work recovery, not exactly-once external execution.

Clip completion recovery remains separate and unchanged. When a completed analysis has pending/failed billing or notification work, or an uncharged failed analysis needs preview cleanup, the existing `reconcileClipRecommendations` path creates a recovery job from the saved recommendation and original `queueJobID`. It resumes the outstanding completion/cleanup step without starting another initial analysis. This existing reconciliation does not make an expired, uncertain analysis claim safe to rerun.

## Legacy acceptance and rollout/rollback boundary

An old permanent Redis acceptance marker by itself contains no job payload. During upgrade it is preserved as `legacy_accepted`; the system does not invent a payload or automatically replay that old accepted job. If an actual legacy Redis payload is still present and consumed, the worker can adopt that payload into Mongo before processing. If both the payload and old marker are already gone, there is no safe reconstruction source.

Roll out the cron consumers first, then the API producer. New consumers adopt actual Redis-only payloads from old producers. Do not run the new API producer with old cron consumers: an old worker may process a queue payload without updating its Mongo intent, leaving a `queued` intent that a later recovery pass can publish and execute again. A future bot producer would require the same consumer-first rollout, but no bot producer is part of this release.

For rollback, first stop or roll back the new API producer, then keep the new cron consumers running until outstanding durable `queued` and `processing` intents have been inspected and explicitly reconciled. Rolling back cron is not automatically safe while such intents remain: a legacy cron worker does not acknowledge Mongo state. A cron rollback requires an explicit read-only pending-state assessment and a reviewed handling plan; there is no automatic data migration that makes a queued intent safe for an old consumer. An immediate cron rollback is safe only before any new durable job intent has been accepted.

## Cutover timing and legacy recovery boundary

At 00:15 UTC on 2026-11-02, read-only inspection found approximately 150 weekly jobs queued under the existing scheduler; 76 remained at 00:46 UTC and 33 at 01:00:56 UTC. The legacy worker uses `BLPOP` without an in-flight receipt; a cron restart between 00:15 and 00:59 UTC could lose payloads already popped by the old worker, and legacy scheduler startup in that interval could reschedule weekly jobs that had already completed. The new memory worker uses a processing list to adopt and recover legacy payloads still queued, but it cannot retroactively recover payloads already popped by an old worker or identify old completed jobs that have no receipt. The cutover was deferred until after 01:00 UTC and the queue drained; the pre-cutover readback then showed empty queues, avoiding the identified exposure. This remains a limitation for payloads already popped by an old worker and completed jobs without receipts.

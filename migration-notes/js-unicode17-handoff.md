# JavaScript Unicode 17 preparation handoff

**Status: verified source-bound Unicode 17 reference data and shared Rust string core; no caller adoption or deployment.** The pinned generator and its independent data readback passed. The Rust core's exhaustive lowercase and fold replay passed against the accepted reference. This still does not verify or complete the separate JavaScript-facing normalization adapter or its callers. See the [dated verification note](js-unicode17-2026-10-29.md) for exact results and limits.

The required Node executable is 24.22.1, V8 13.6.233.17-node.58, ICU 78.3, Unicode 17.0, SHA-256 `569128f3066ac7be59b10b9a0adef708def642ee37cbf9d560a9bdb68f872108`; the source-root TypeScript SDK must be 5.9.3. `--write` uses exclusive creation and requires an empty directory; `--check` requires exactly those two regular files and compares generated bytes. No directories are created. The output paths must be canonical and outside the source root. Do not run with live resources or make the output directory a production mount.

The complete TypeScript source shape, including the two exports, types, normalization argument, regular expression, and method sequence, is checked with the pinned compiler's AST printer; the actual transpiled source is sanity checked in a VM. The mark regex comes from that AST with `g` removed, and is checked against the general category `M` predicate across all code points. The remaining Unicode properties are dependencies of default case conversion, rather than application-specific policy. All integer code points, including lone surrogate values, are observed with the actual built-ins. Sparse NFD reference entries include Hangul for later exhaustive parity checking, but are excluded from the generated runtime Rust tables.

Unicode default casing has only the locale-independent contextual Final Sigma mapping; context goldens use the actual built-in for every `Cased` and `Case_Ignorable` overlap, on both sides of sigma, with both surrounding cased states and barriers. A future context scan must test `Case_Ignorable` before `Cased`, because the properties overlap (for example U+0345). These are empirical inputs and expected outputs, not a substitute JavaScript casing algorithm.

The accepted core uses the existing `unicode-normalization` 0.1.26 NFD implementation, whose data is Unicode 18, only within Unicode 17 assigned scalar runs. Unicode 17 unassigned code points and surrogate units are barriers; the Unicode 17 Mark table is applied after NFD. This passed exhaustive actual-Node comparison. NFD stability for characters assigned in both versions is described by [UAX #15](https://www.unicode.org/reports/tr15/); Unicode 17 property and casing data are specified by [UnicodeData.txt](https://www.unicode.org/Public/17.0.0/ucd/UnicodeData.txt), [DerivedCoreProperties.txt](https://www.unicode.org/Public/17.0.0/ucd/DerivedCoreProperties.txt), and [SpecialCasing.txt](https://www.unicode.org/Public/17.0.0/ucd/SpecialCasing.txt). No Rust standard-library Unicode version is assumed, and no standard-library mismatch was reproduced. See the [verified core handoff](js-unicode-core-handoff.md) for its behavior and API; it does not cover JavaScript input coercion or source caller adoption. The generator and the core proof make no performance claim.

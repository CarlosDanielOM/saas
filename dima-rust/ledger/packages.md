## Crate map (decided)

Dependencies point downward only. Library crates take typed configuration structs; only binaries read
the environment.

| Layer | Crate (path) | Holds |
|---|---|---|
| 0 | `dima-text` (`crates/text`) | Text rules, JavaScript-visible formatting, canonical JSON, ordering |
| 1 | `dima-core` (`crates/core`) | Environment parsing helpers, errors, clock and randomness, shutdown, crypto, ids |
| 1 | `dima-store` (`crates/store`) | MongoDB and Dragonfly connections, BSON rules, JSON for HTTP, Lua, queues, pub/sub, fences |
| 2 | `dima-telemetry` (`crates/telemetry`) | Logger, trace context, metrics, span and log export |
| 2 | `dima-http` (`crates/http`) | Outbound HTTP: timeouts, retries, SSRF guard, provider base URLs |
| 2 | `dima-web` (`crates/web`) | Inbound HTTP edge with Express semantics |
| 2 | `dima-socketio` (`crates/socketio`) | Socket.IO server with connection state recovery, on `engineioxide` |
| 3 | `dima-model` (`crates/model`) | Document types, collections, indexes, write helpers (timestamps, `__v`, defaults) |
| 4 | `dima-twitch`, `dima-events`, `dima-billing`, `dima-email` | As in `modules.md` |
| 5 | `dima-stream`, `dima-tts`, `dima-ai`, `dima-commands`, `dima-platform` | As in `modules.md`; `dima-stream` is what `modules.md` calls `dima-analytics` (stream sessions and analytics, timeline, site analytics, raid analytics, follow ledger): the name `dima-analytics` belongs to the service in `services/analytics` |
| 6 | `dima-engine` (`crates/engine`) | The command language, pure: syntax, evaluator, blocks, pure functions, host trait |
| 7 | `dima-actions` (`crates/actions`) | Command effects, chat delivery, special parser, AI chat and tools (the rest of the engine cycle) |
| 8 | `dima-realtime`, `dima-chat`, `dima-services`, `dima-event-handlers`, `dima-site-agent` | As in `modules.md` |
| 9 | `api/`, `bot/`, `cron/`, `services/*` | Binaries: wiring only |
| - | `rig/` | Side-by-side rig and service mocks (development tool) |

Decisions behind the map:

- **No vendor SDK crates.** Twitch, OpenRouter, Polar, Resend, PostHog, OTLP logs, Qdrant (REST, as the
  TypeScript does), S3 and the rest are thin clients on `dima-http`. One HTTP stack, one TLS provider,
  small binaries, and every call can be pointed at the rig's mock by configuration.
- **Own router.** `dima-web` implements Express's ordered dispatch (registration order, case-insensitive
  paths, optional trailing slash, mounts, pathless middleware, error handlers), so route tables are
  ported one to one. axum/hyper are used underneath.
- **Own Socket.IO layer, limited to what the clients use.** `socketioxide` 0.18 has no connection state
  recovery (checked in its source), and three overlays loaded in OBS (triggers, clips, furry) show
  events replayed after a short disconnect and fetch nothing themselves. `dima-socketio` implements
  Socket.IO protocol revision 5 on top of `engineioxide`: text events and acknowledgements, static
  and pattern namespaces, recovery for the namespaces that have it today; no rooms beyond a socket's
  own, binary packets refused. Evidence, the options weighed and the design are in `socketio.md`.
- **The engine cycle is split in two.** The 61-file TypeScript import cycle becomes a pure engine crate
  with a host trait, and an actions crate that implements the host.
- **Reference captures.** The rig records the frozen reference once and stores the captures; candidates
  are verified against them. The captures remain the regression suite after the TypeScript is deleted.
- **One cutover.** Rust never runs beside TypeScript. Dragonfly encodings are Rust's own; each key
  family is drained, rebuilt or carried at cutover (the porting package says which). MongoDB writes stay
  compatible through the store helpers.
- **Time is epoch milliseconds** (JavaScript `Date` semantics) end to end; calendar and time-zone maths
  use a library only where the reference does such maths.

## Phase 2: the old crate drained into the workspace

The old single crate (`dima-rust/src`, 36,000 lines without tests; inventory in `existing-rust.md`) is
moved module by module onto the foundation, converted to native UTF-8 and brought up to today's
reference. A module is deleted from the old crate by the package that replaces it. Corpora are
regenerated from the TypeScript with Node 24; an intended difference from recorded JavaScript
behaviour is written as code in the test, never by editing a recorded expectation.

## Pace

The plan's usage is readable in T3 Code's provider cache (`~/.t3/caches/claudeAgent.json`,
`usageLimits`: a five-hour window and a weekly one). The weekly limit is the binding one: measured on
2026-11-11 with ten Opus workers, 40 minutes took 19% of a five-hour window and 5% of the week, so a
full window costs about a quarter of the week. The week resets on Saturday 2026-11-14 at 18:00 MST.

Owner's rules (2026-11-11, 22:15 MST):

- Full speed until the weekly figure reaches 75%, then slow down until 95%, then stop until the reset.
- The five-hour window must never reach 100% (workers die in the middle of a task, as happened once):
  the lead reads the figures before every launch and keeps it under about 90%.
- Night, 23:00 to 07:00 MST: four GPT-6.1 Sol implementers and two Opus. Day, full throttle: six Opus
  and two Sol implementers; day, slower: three and three. Sol as a daytime implementer is on trial
  until about 2026-11-12 22:30 MST (the owner pulls it back to nights if it slows progress); Sol
  also keeps reviewing. Sol gets well-specified or self-contained packages (the small services,
  thin API wrappers, email, model batches); Opus keeps money, tokens, the engine and data integrity.
  Every result, whoever wrote it, is merged, gated and reviewed the same way.

Other limits: the laptop's memory, the two build slots, and the lead's own integration (merge, gate,
review of each result). `high` unless a package is truly hard; every brief tells the worker to commit
as it goes.

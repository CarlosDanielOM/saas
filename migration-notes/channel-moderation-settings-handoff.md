## Source and native mapping

The source module exports `ModerationRuleType`, `ModerationAction`, `CapsThresholdMode`, `IModerationOffenseStep`, `IModerationRule`, `IChannelModerationSettings`, three defaults objects, six limits, `buildDefaultModerationRules`, and the Mongoose `ChannelModerationSettingsSchema` model. The native module maps the three enums, public record/policy types, three defaults, six limits, and rule builder. `schema()` exposes the schema definition; `get_channel_moderation_settings_model(&Database)` constructs the concrete repository against an explicitly supplied database. It does not register a global model or connect during construction.

The TypeScript source imports spam-category values and `crypto.randomUUID` at runtime, along with Mongoose `Schema`/`model`. Its `SpamProtection`, `ModerationVariations`, `PermissionExpression`, `ModerationPattern`, and `SemanticPolicy` imports are type-only. Rust reuses the native spam category/protection types, `CapsThresholdMode`, `JsString`, and the existing UUID v4 crate. Malformed permission expressions stay a BSON Mixed value; the schema itself does not inspect their meaning. UTF-16 strings convert to BSON UTF-8 with replacement for lone surrogates, matching the documented boundary.

The rule builder makes four rules in source order. All four share the same offense-step objects and the `allowlistDomains` and `terms` arrays within one call because the TypeScript code shallow-spreads a common base; a later call gets fresh objects and arrays. The Rust builder models this bounded sharing with `Arc<Mutex<...>>`, and creates source-order UUID v4 values. Defaults preserve the `warn`/`delete`/`timeout` offense ladder, all six public limits, rule reasons and thresholds, and the default spam-category/tag lists.

The schema maps `_id: false` nested subdocuments, required `channelID`, collection/model name, `__v`, timestamps, and the unique `channelID` index. It preserves the source defaults and constraints for rules, spam protection, categories, exempt tags, patterns, semantic settings, and variations. `FieldDefault::Value` and `ArrayElement` are used only where required for nonempty composite defaults and per-element enum validation; Mixed minimization is explicitly enabled for the source's expression and variations fields.

## Evidence and boundaries

The pinned actual-source oracle executed the unchanged TypeScript model and actual spam-category module with a disconnected Mongoose 8.24.2 instance and real Node crypto. It independently records and checks source/native/SDK/Node hashes, dependencies and type-only imports. The accepted checks matched 97 schema-core cases, four selected source-model records, and 56 full actual-model cases. Six new ordinary tests, two source replay tests, the private Mongo repository test, and the existing application persistence test passed. Existing core/application/channel-TTS and additional regressions passed as well. The final strict workflow covered formatting, no-feature, Mongo/Redis, all features/all targets, and Clippy.

The Mongo fixture exercised the concrete unique index, insert, read, duplicate rejection, update, and updated timestamp using an explicitly task-owned disposable database. It passed alongside the existing application Mongo persistence check. Cleanup is constrained to the fixture's owner-named database collections and marker. Final evidence reports all 19 production records unchanged and no remaining task-owned resources.

The source and Rust model remain in the application tree; this is not a TypeScript retirement or caller cutover. The implementation is a concrete local schema and repository mapping for the typed BSON/ordinary JSON contract. It does not implement arbitrary JavaScript prototypes, executable Mixed hooks, sparse or undefined array slots, or exotic constructor metadata as generic Mongoose behavior. The Mongoose model is global in TypeScript while the Rust repository requires a caller-provided `Database`, so application initialization and caller adoption remain separate work. Overall Rust migration remains incomplete. No performance measurement, deployment, or push is claimed.

No changes were made to Cargo dependencies or the Rust toolchain. The accepted verification used the existing capped isolated compiler path; its reported 156.944-second phase-inclusive run is recorded as a resource/receipt fact, not a build-speed or runtime-performance comparison.

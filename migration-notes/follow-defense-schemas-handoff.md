# Follow defense schema authoring handoff

**Status: verified local schema/type batch; source retirement accepted.** Commit `bb4bf87f17485d81e9d244cbd59ae9406851ccec` retired the three follow-defense TypeScript schema sources byte-for-byte and verified all four concrete native models, actual-source replays, private Mongo CRUD/index/projection/write-concern behavior, and strict checks. See [the functional migration batch note](functional-migration-batches-2026-10-30.md). Caller adoption and deployment remain separate.

The authored wiring and verification instructions below are historical and superseded by the accepted batch. Preserve their model-specific schema details as implementation context; do not treat their pending checks as outstanding work.

The three source modules export four models. `follow_attack_log` uses an ObjectId root, timestamps, version key and journaled write concern; it declares `FollowDefenseMode`, `FollowDefenseTriggerSource`, `IFollowAttackTrackedFollow`, `IFollowAttackRaidInfo` and `IFollowAttackLog`. Nested follow and raid subdocuments have no generated IDs. `follow_defense_action` exports the inferred `FollowDefenseAction` and action and durable-control models; both use string `_id`, no version key and journaled concern. Action timestamps and the zero-second TTL on `purgeAt` belong only to actions. Controls have no TTL. `follow_hate_raid_source` uses an ObjectId root, timestamps and version key; its optional ObjectId receipt array has no default and is excluded by default projection, and the target/raider pair is uniquely indexed.

Reuse discovery: `follow_defense_baseline.rs` already reads `follow_attack_logs`; `raid_sessions/moderation.rs` already uses `follow_defense_actions` and `follow_defense_controls`. Its private, narrow `Control` projects only `cancelledThrough`, and `values.rs` contains `action_document` and `control_defaults` for that execution path. Those are not complete public schema DTOs and were not modified or duplicated as execution policy. The draft uses `SchemaDefinition`, `SchemaIndex`, `SchemaRepository` and existing driver-backed collection construction for all four models, including the shared journaled write concern and hidden projection. The optional typed-value module uses the concurrently authored `ordinary_model_values::{Reader, StrictDecodeError, insert_string, insert_optional_string, insert_f64, insert_optional_f64, insert_datetime, insert_nullable_datetime}` helpers for string/date/BSON projections, plus shared `bson_compat::js_number`. This helper is an open shared dependency: the parent must validate and commit the concurrent ordinary-model helper first, then validate and commit this dependent slice separately. The strict DTOs reject explicit null for source optional properties while raw BSON schema documents retain null versus absence; valid unknown fields are handled by the schema core's source strict-model behavior. Unpaired UTF-16 strings are replaced only at the BSON write boundary. Typed Number accepts non-finite binary64; unpromoted BSON Long outside ±2^53 is rejected as a typed JS-number view. Platform-specific error stack behavior is outside the contract.

The benchmark drafts prepare four 32-item valid model pools using actual source construction and validation, fixed ObjectIds and dates, full BSON preflight and constant-time scalar checksum. Decode, fixture reads and process startup are excluded; inputs are predecoded on both sides and the comparison is limited to these different public model boundaries. Cross-runtime wire/document equality and checksums are required before the samples are meaningful. Each 32-item pool varies a scalar ID/channel while preserving the same model shape; these are narrow prepared workloads, not a representative population. Both benchmark halves and their preflight remain unexecuted; no numbers or speed claim are available.

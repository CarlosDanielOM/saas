# Mongoose Date casting — 2026-10-28

## Scope and status

This bounded Rust addition ports Mongoose 8.24.2 Date casting for ordinary application values and routes the shared Rust schema caster's `FieldType::Date` arm through it. It is opt-in under `application-schemas`; it does not change default features or worker profiles. No crate or version was added, and `Cargo.lock` is unchanged. The migration remains incomplete: the 14 archived baseline leaf helpers are unchanged, no TypeScript caller was retired or switched to this caster, and no live adoption occurred. This feature does not establish full Mongoose casting or schema parity.

The shared caster applies to the 42 Rust application models selected by `application-schemas`. Reuse was direct: `schema.rs` already centralizes per-field casting, while `utils::json_number::string_number` and the preceding `js-date` port provide numeric-string coercion and date parsing. The remaining gap was Mongoose's Date-specific coercion, null behavior, and `TimeClip`; this module fills that gap without adding a parallel schema path. The `js-date` parser is shared with other date consumers but does not itself implement Mongoose casting.

## Implemented behavior and boundaries

For supported BSON representations of ordinary JavaScript values, `mongoose_date::cast` handles null and empty-string-to-null, numeric values, numeric-looking strings, legacy and ISO date strings, arrays through ordinary primitive stringification, plain objects that lack own `toString`/`valueOf` overrides, invalid-date rejection, and `TimeClip` truncation and range checks. Numeric strings use Mongoose's asymmetric numeric threshold (`>= 275761` or `< -271820`) before falling back to the JavaScript date parser. `Int64` is rounded to binary64 before casting, matching JavaScript Number representation. Boolean inputs fail as date casts. The common schema layer retains path-specific `cast` and `required` errors.

The adapter's input model is deliberately narrower than arbitrary JavaScript objects. BSON `Int32`, `Int64`, and `Double` stand for JavaScript Numbers; BSON DateTime stands for a JavaScript Date. BSON arrays and documents cover ordinary arrays and plain objects without executable coercion hooks. BSON can represent DateTime values inside arrays, but this caster does not implement the matching JavaScript `Date.toString()` coercion used by Mongoose for those array elements. It also cannot represent overridden coercion methods or BSON prototypes such as an unpromoted BSON Long object. Callers that handle such values must adapt them before this API. The test oracle's explicit boxed-number/date cases are encoded into their corresponding BSON stand-ins; this is not a general BSON-to-JavaScript bridge.

Date-string parsing inherits the `js-date` adapter's Linux libc and configured zoneinfo behavior. It assumes the process timezone stays fixed, uses a fast path only for exactly `TZ=UTC`, and requires host zoneinfo to match the pinned Node ICU timezone data for exact local-time parity. The Node oracle uses bundled ICU 78.3 with tzdata 2026e; the isolated Rust compiler uses the task-owned OS package tzdata-2026e-r0. This integration does not establish behavior on other operating systems or in the production runtime image, whose timezone data has not been validated for this caster.

## Source and fixtures

The reference fixture creates a fresh Node process for each of UTC, America/New_York, Europe/Berlin, Australia/Lord_Howe, and Pacific/Apia. It exercises the actual Mongoose Date caster, a disconnected synthetic Date schema (including required/default behavior), and the actual `admin.schema.ts` model. Inputs include empty and whitespace strings, numeric-looking strings around the threshold, ISO and legacy dates, invalid values, numbers and boxed numbers, Date values, arrays and plain objects, and the TimeClip boundaries. The fixture records hashes for the oracle source, admin schema, and Mongoose's date caster, schema Date, schema type, and cast-error modules.

The native behavior test compares the direct caster and shared Rust schema constructor with the generated source outcomes for each selected zone. It separately exercises the actual native admin schema. Required and default cases are checked independently. A second ignored test uses an explicitly supplied, freshly named task-owned MongoDB database and the real admin repository insert/save/find path, checking persisted BSON date/null types, partial-save preservation, timestamp hooks, and rejection without unintended writes. The ignored MongoDB test requires the exact-candidate fixture run to count as persistence evidence; its existence alone is not a pass.

The source-matched final run passed 80 cases across the direct caster, synthetic schema, and actual admin schema in all five timezones (1,200 case/path comparisons), plus missing-required/default checks. It recorded 64 ordinary Rust executions, three explicit disposable MongoDB fixtures (the new admin persistence path and two existing schema fixtures), and four explicit release benchmark runs. The final compiler and Node receipts share source-tree SHA-256 `95b1258b52f1569839461f7954eb2e1267c75c605e1167a8bc1feeba601e1078`; see the [evidence pack](evidence/2026-10-28-mongoose-date/README.md) for exact breakdowns, source hashes, compiler limits, and raw artifacts. A negative control that restores only the pre-integration `schema.rs` fails on JSON string `"0"` at path `d`, confirming the old shared integration missed this behavior. It is an intentional expected failure, not a final-candidate regression.

## Measurements and adoption

The paired synthetic benchmark uses UTC inputs selected from the same generated Mongoose fixture. It compares the actual Mongoose caster with the release Rust BSON helper for numeric, string, invalid, and mixed workloads. Each sample runs 10,000 operations after one 10,000-operation warmup; seven measured samples are collected per workload. Fixture decoding, preparation, JSON, and file I/O are outside the measured loop. Output checksums and valid/null/invalid counts establish comparable results. Mongoose throws and allocates assertion errors with stack details for invalid inputs; Rust returns typed errors without formatting those details. Timing therefore describes these specific loops, not equivalent production error handling or an application error rate.

All four synthetic caster workloads had matching per-sample checksums and valid/null/invalid counts. Median Rust/Node times were 0.0164/0.1841 µs per operation for numeric, 0.20595/0.29686 for string, 0.05617/47.1122 for invalid, and 0.08896/17.1099 for mixed. The invalid and mixed measurements include Node throwing stack-bearing assertion errors while Rust returns unformatted typed errors, so their very large differences do not compare equivalent error detail. The mixed fixture is 37.5% invalid, and the Rust numeric path avoids JavaScript Date object allocation; these implementation-shape observations are not isolated causal timings. No production latency, throughput, CPU, RSS, or error-rate conclusion follows. See the [evidence pack](evidence/2026-10-28-mongoose-date/README.md) for exact medians, ratios, receipts, source hashes, resource limits, and raw artifacts. There is no caller cutover, TypeScript retirement, or deployment in this feature record.

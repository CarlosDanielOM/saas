## Pet queues (2026-10-26)

Independent pet actions queue instead of failing `busy`; the "one active request, no backlog" rule below now describes only the single **active** slot. Admission (bot/cron/API) never takes that slot: it validates as before, still rejects a missing player (`player_unavailable`, like TTS without an overlay), then stores a durable `status:'queued'` row with a 10-minute `phaseDeadline` (`PET_QUEUE_WAIT_MS`). Only the API runtime starts queued rows, using the same runtime compare-and-set fences as before (no active request, no pending TTS reservation, same lease) in `pets/queue.ts` `claimQueued`. A promoted row becomes `accepted`/`admitted` with the current generation and settings revision, then follows the unchanged provider/delivery path. Settings that turned the action off end a queued row (`pet_unavailable`, `pet_source_disabled`, `trigger_disabled`, `text_too_long`); overdue rows expire through the existing bounded recovery. Legacy unadmitted `accepted` rows still resolve through the original duplicate path.

Two lanes (`PetRequest.lane`):

- **`tts`** — `$(pet.talk)` always, and `$(pet.ask)` when `behavior.askLane:'tts'`. The producer writes the row and one normal Redis TTS queue item (`speechID` `PET` + 13 hex, score = admission time, payload `pet:{requestId,ownerId,operation}`, same stream-session tagging), so the pet speaks in exact arrival order with normal TTS. The TTS queue limit (`queue.maxItems`) applies and `queueLength` includes these items. When the API TTS queue reaches the item it calls the registered pet-lane bridge (`pets/tts_lane.ts`): the runtime waits up to 120 s for the pet to be free, ignoring the pet cooldown, and skips the item if the player or appearance is unavailable so normal TTS keeps moving. The queue holds its processing lock until the pet request is terminal (240 s watchdog). TTS skip/clear/refresh/timeout cancel the pet request exactly like a dashboard cancel (lease invalidated). A pet head needs the pet player, not a speech overlay; later normal items still wait for an overlay. Stream-end backlog clearing removes the Redis item and the row expires.
- **`independent`** — `$(pet.ask)` by default (`askLane:'independent'`). FIFO by `createdAt` per owner, limited to `behavior.queueSize` (1–10, default 5; concurrent producers resolve by FIFO rank, losers end `failed/queue_full`). `cooldownSeconds` is now the pause between queued replies; a timer wakes the owner when it ends. A waiting TTS-lane turn takes the free pet first. This lane does not hold up normal TTS.

Configuration adds `behavior.queueSize` and `behavior.askLane`; missing values normalize on read. New AST error codes: `queue_full`, `queue_unavailable` (Redis enqueue failed). Checks: `src/pets/admission.test.ts`, `src/pets/queue.test.ts`, `src/handlers/tts_pet_lane.test.ts`, and the candidate check `ops/checks/pet-queue.mjs` (with the pet-runtime fixtures).

## Configuration and HTTP

`getPetConfiguration`/`savePetConfiguration` remain the single configuration boundary. Current responses use `schemaVersion: 3`. The accepted DIMA-030 release used schema v2; its deployment receipts and review record above are historical. DIMA-032 adds `sources:{independent:boolean,readTts:boolean}` (defaults `true`/`false`) and `ttsAudio:'pet'|'overlay'` (default `pet`). Missing legacy appearance, playback, sources, and audio fields normalize on read without writing:

```ts
appearance: { kind: 'png' | 'vts', idleAssetId: string | null, talkingAssetId: string | null }
playback: { target: 'browser' | 'desktop', desktopSessionId: string | null, vtsSessionId: string | null }
sources: { independent: boolean, readTts: boolean }
ttsAudio: 'pet' | 'overlay'
```

Default target is browser, kind PNG, IDs null. PNG uses two original image/animation uploads from the private Asset Library. Images must belong to the channel owner, be ready and have PNG/JPEG/GIF/WebP MIME. Referenced images cannot be deleted. Existing saved offline desktop selections may remain; new selections must name a connected, freshly authenticated session owned by the same account. Audio and VTS selections are independent. Effective personality reads only explicitly selected persona/rules; no moderation tools or bot memory/known-user context is shared. Changes to the selected profile/rules invalidate active work, as do settings saves and output changes. Required appearance is checked for independent pet admission and again before each independent provider dispatch: PNG requires owner-valid ready image references (`appearance_unavailable`), VTS requires a selected freshly authenticated connected ready controller (`vts_unavailable`). Read-TTS uses separate readiness; if pet appearance or player readiness is unavailable, normal-TTS synthesis remains separate and the same generated file can fall back to the overlay. Bot/cron independent pet admission reads an API-authored `pet_readiness` row keyed by owner, matching generation, settings revision and selected session. Its expiry is at most 15 seconds after successful validation and never exceeds OAuth access/session expiry. A single API boot-identity record in that collection fences cross-process reads against prior-process proofs. API restart changes that identity and clears owner rows; ready-false, disconnect, selection/generation changes and revocation clear or invalidate them. The API refreshes previously validated owners every five seconds, comfortably before the 15-second proof expiry, and coalesces concurrent refreshes through one in-flight owner observation. An older ready-false/disconnect clear cannot land after a newer ready write. Refreshes neither change settings revision nor broadcast unchanged state. Producers do not publish readiness. Independent API dispatch still requires the actual authorized local VTS peer immediately before each provider call. Browser audio election in PNG mode additionally requires renderReady. Losing the selected VTS controller invalidates active independent pet work and playback.

Dashboard paths retain `{error:false,data:...}` / `{error:true,message:stable_code}` envelopes:

- `GET/PUT /pets/:channelID/settings` (PUT `{revision,settings}` optimistic concurrency).
- `GET /pets/:channelID/runtime` returns data `{v:1,generation,active,sessions:[{sessionId,label,audioReady,vtsReady}]}`. Only connected authenticated desktops belonging to this owner appear. Same-session sockets aggregate readiness with boolean OR; they remain one candidate.
- `GET /pets/:channelID/overlay-token`; `POST` with `{}`, `{rotate:true,version}` or `{token}` return `{token,exists,version}` using the shared encrypted overlay-token utility. Creation is idempotent; stale-version rotation conflicts.
- `POST /pets/:channelID/requests/:requestId/cancel` with `{commandId}` is terminal/idempotent. It does not promise a refund.
- `GET /pets/public/:capability` returns `{appearance,playback,runtime,assets}` within the dashboard envelope. It exposes no prompt, credit balance or session list. `playback` here discloses only the target. `GET .../assets/:assetId` authorizes current configured images then streams original private bytes, with no-store.
- `GET /pets/playback/:requestId/audio?ticket=...` streams private WAV/MP3 with no-store. A five-second opaque ticket is bound to owner, connected peer/session or capability version, request, generation and lease. Each fetch revalidates current authority; it is unusable after cancellation, rotation, expiry or disconnect. Audio files live in task-created directories outside served public speech paths; terminal/recovery cleanup removes them.

OAuth resource responses are unwrapped:

- `GET /v1/me/pet`: configuration without dashboard profile/voice pickers; requires `pet:read`.
- `GET /v1/me/pet/runtime`: same inner runtime shape; requires `pet:read`.
- `PUT /v1/me/pet/playback`: `{commandId,revision,roles:['audio'|'vts',...]}` requires `pet:playback:select`. Selects the caller's own connected OAuth session; caller-supplied session/account IDs are rejected. Returns configuration. A retried save whose revision already advanced once and whose requested selections match is harmless.
- `POST /v1/me/pet/requests/:id/cancel` with `{commandId}` requires `pet:control`.

Active OAuth permissions are the original `profile:read credits:read desktop:connect` plus `pet:read pet:receive pet:control pet:playback:select`. Existing grants/sessions never gain scopes; fresh explicit consent is required. `pet:interact`, `pet:write`, `usage:read` remain inactive. Metadata adds `beta.socket_io:{path:'/socket.io/',namespace:'/desktop',protocol_version:1}`. `/v1/desktop/session` retains identity/device/expiry fields and `protocol_version:1`, sets `pet_available` from `pet:receive`, and adds the same `socket_io` object.

Migration overlap: native `/v1/desktop/ws` heartbeat and its metadata advertisement are retained while the new desktop is integrated and accepted. The new pet path never falls back to it. Parent owns review/removal after coordinated Socket.IO acceptance; indefinite dual-protocol operation is not the product goal.

## Socket.IO v1

Path `/socket.io/`; static namespaces `/desktop` (auth `{v:1,accessToken}`) and `/pet` (auth `{v:1,capability}`). No token/capability URL query authentication, recovery, packet replay or resumed playback. Server construction now selects the ordinary exported `socket.io-adapter` `Adapter` for exactly these two names. No session/packet retention buffer or recovery timer is constructed for them; reliable events remain exactly `[event, object]` with no recovery offset. Other namespaces still receive the same `SessionAwareAdapter` as before. Global Socket.IO recovery and all other site/overlay policies remain as before. Pet attempts to provide recovery pid/offset must authenticate afresh and are rejected by the exact auth schema. Desktop pet sockets require `desktop:connect pet:read pet:receive`. Maximum two sockets per OAuth session, 16 peers per owner, 1024 total. Revocation/access expiry/plan changes are revalidated on messages, renewals, media requests and at most every 15 seconds while idle.

All `serverTime`, `expiresAt` and `startBefore` wire values are **numeric epoch milliseconds**. Lease duration values/positions are numeric milliseconds. Desktop hello is `{v:1,sessionId,channelId,scopes}`.

```ts
RequestView = { requestId, operation: 'talk'|'ask'|'tts', status, version, text?, errorCode? }
// 'tts' is Read-TTS's normal-queue handoff; it reuses synthesized normal audio, not a pet-provider synthesis request.
// text is optional resolved output text.
// status: accepted|generating|synthesizing|ready|playing|completed|cancelled|failed|expired
pet:snapshot = { v:1,serverTime,peerId,generation,settingsRevision,appearance,playback,
  sources:{independent:boolean,readTts:boolean},ttsAudio:'pet'|'overlay',
  assets:{idleUrl:string|null,talkingUrl:string|null},active:RequestView|null,
  lease:{leaseId,holderPeerId,expiresAt}|null }
pet:request = {v:1,generation,request:RequestView}
pet:play = {v:1,requestId,generation,leaseId,startBefore,
  audio:{url,mimeType:'audio/wav'|'audio/mpeg',durationMs}}
pet:stop = {v:1,requestId,generation,reason}
```

Clients send `pet:ready {v:1,audioReady,renderReady,vtsReady}`, `pet:lease {v:1,action:'acquire'}` or `{v:1,action:'renew',leaseId,generation}`, `pet:playback {v:1,requestId,leaseId,generation,seq,phase,positionMs,errorCode?}` with phase started/progress/ended/stopped/error, and `pet:mouth` with the same identity/seq/positionMs plus finite value 0..1. Playback and mouth each use strictly increasing **request-scoped** sequence counters. Mouth input is at most 25 samples/second while actually playing; progress is at most five samples/second and never rebroadcasts unchanged renderer state. Only the elected audio peer may report either stream. Exactly one eligible selected VTS peer (lexicographically smallest server peer ID) receives mouth values, including when multiple sockets use one session.

Acks: `{ok:true,data:T}` or `{ok:false,error:{code,retryAfterMs?}}`. Lease data: `{leaseId,generation,serverTime,expiresAt,ttlMs:15000}`. Renew every five seconds. Clients stop on disconnect/local conservative expiry. A previous lease's full conservative expiry forms the new-generation handover barrier even when the old socket was disconnected. Only the elected peer receives one play emission after synthesis; reconnect snapshots never re-emit play. A client must never queue/replay a duplicate request. Server limits audio to **60 seconds / 8,000,000 bytes**, stricter than any defensive client ceiling.

Ready messages that change no state publish nothing. A bounded per-socket control queue admits ordered bursts such as ready/acquire. Mouth/progress samples are lossy/coalesced by dropping obsolete busy telemetry with `{ok:true,data:{dropped:true}}`; they never create an unbounded promise queue or force an audio stop. One queue slot is reserved for a terminal acknowledgement. The elected peer receives a ready `pet:request` immediately followed by its sole `pet:play`, synchronously on the same socket. Per-peer read serials invalidate snapshots assembled before this delivery; request versions and bounded retired identities reject regressions and terminal resurrection. These server guards complement the real client’s monotonic guards. Owner wake notifications coalesce through a dirty flag while a broadcast runs; snapshots are serialized by owner. Generating/ready/playing and terminal request changes are persisted and broadcast. Public PNG rendering follows actual authorized playback started/end/error/stopped, independently of which browser/desktop owns audio.

## Internal production trigger boundary

```ts
import { admitPetAction, type AdmitPetActionInput } from './pets/admission.js';
interface AdmitPetActionInput {
  channelId: string; operation: 'talk'|'ask'; text: string;
  origin: {kind:'chat-command'|'twitch-event';id:string;occurredAt:string};
  actionKey: string; actor:{userId:string;displayName:string};
}
// => Promise<{requestId:string,status:string}>
```

The configured AST integration derives identity from the real command/event effect context, not user text: Twitch message_id/eventKey, stable engine actionKey, server account/channel and actor. Missing identity rejects. Configured chat/event actions are gated by respondToChat/respondToEvents; there is no unconditional chat listener. The configured tags are `$(pet.talk supplied text)` (direct TTS) and `$(pet.ask supplied prompt)` (no-tool LLM then TTS). Tags return empty text on admission and bounded errors on rejection; LLM output is never AST-evaluated. Producers admit durable state + Redis wake only; no provider work runs in bot/cron.

One active request per pet (queued requests wait outside this slot; see Pet queues above). Mongo has a unique `(ownerId,origin.kind,origin.id,actionKey)` index. Identical payloads reuse one request; changed payload conflicts. An explicit admitted flag closes the insert/runtime-CAS gap: creators/duplicates may resolve the same sole slot, but none returns accepted before durable linkage. If a duplicate read admitted=false and the winner already advanced, the loser rereads and returns the admitted generating/terminal outcome instead of falsely expiring it. A runtime claim carries a unique internal claim ID and captures the atomic runtime preimage. If a delayed duplicate successfully reclaims an already terminal request, it conditionally clears only its own slot and restores the preimage cooldown. The predicate uses the immutable lease identity, never its renewable expiry; lease renewals survive cleanup. Replacement requests and same-millisecond competing claims remain untouched. Normal acceptance and active-pointer invalidation clear claim ownership. Rejection CAS only touches an unadmitted accepted row. Request-specific cancellation compares expected request ID and generation atomically; completion/replacement of A cannot invalidate B or its lease/readiness. Recovery never synthesizes unadmitted rows. Active phases are persisted before provider calls. Unknown provider outcomes after crash become terminal `provider_outcome_unknown`; reconnect/recovery never regenerate them. Dedupe records expire after seven days, which bounds replay protection to that retention window.

The existing no-tool `generateStandaloneText`, model policy, verified `getAiCredits(...,{requireVerified:true})` and exhausted/unavailable TTS fallback rules are reused. Paid calls are single-attempt for pets; private provider options do not change default normal-TTS output/fallback behavior. Stable separate usage IDs are `requestId:llm` and `requestId:tts`, source pet, using existing durable usage ingest/debit idempotency. LLM/TTS usage failures end the request rather than rerun providers. Cancellation aborts supported provider work and invalidates playback, without promising refunds for work already accepted upstream.

Redis hints use the existing `DomainEventWakeups` lifecycle through a pet-topic adapter: producer notification only schedules work; it never awaits connection/publication. One client/command, one pending bit and at most 64 coalesced owner IDs are retained. Dedicated hint clients use 500 ms connect/command deadlines, disable offline queues/automatic reconnect and destroy failed clients to flush commands. API subscriber startup is also asynchronous; failed hints are dropped and bounded Mongo recovery remains authoritative. The shared `DOMAIN_EVENTS_WAKEUPS_ENABLED=false` switch also disables these reused hint clients. Redis hints are advisory after durable admission. API recovery uses one guarded 15-second timer, indexed/limited 64-row expiry/accepted/cleanup scans and one indexed runtime-header read for at most 64 rotating connected owners to repair missed selection/terminal hints; unchanged idle owners do not generate snapshots, no idle high-frequency polling. At most four provider tasks run at once across owners. Files/directories for completed requests are removed on bounded recovery. The DIMA-030 candidate's separate Rust/client ordering and producer catalog checks were still outstanding at that historical handoff; DIMA-032 API, bot, and cron consumer checks passed as recorded above. Real account/provider playback, browser autoplay, desktop platforms and VTS still need acceptance; no production provider credentials were used.

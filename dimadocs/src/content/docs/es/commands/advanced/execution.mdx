Lee esta página cuando un comando muestre un error, no haga nada o se ejecute en un orden distinto al que esperas. Explica los pasos que sigue el bot con cada comando y los límites que aplican en cada plan.

## Flujo de ejecución

1. Un comando, una recompensa o un evento inicia la plantilla.
2. Se completan los placeholders. `&p1` es la primera palabra que escribió el espectador, `&p2` la segunda, y así sucesivamente. `&t` es todo lo que va después de la última palabra numerada. Consulta [Sintaxis y datos AST](/es/commands/advanced/syntax/).
3. El bot arma el contexto: el canal, el usuario, el plan y los datos del evento, si los hay.
4. El texto se divide en tokens.
5. Los tokens se convierten en una estructura que el bot puede ejecutar.
6. La estructura se ejecuta de arriba hacia abajo. Las funciones se ejecutan de izquierda a derecha.
7. Las variables se guardan en memoria, caché o base de datos cuando se asignan.
8. La respuesta se publica en el chat. Las referencias a comandos (`#(...)`) se ejecutan después, en orden, cada una con su propia respuesta.

## Quién ejecuta el comando

El contexto incluye el canal, el usuario, el plan y, en los comandos de eventos, los datos del evento. Las funciones de evento como `$(cheer.amount)` leen los datos disponibles en el contexto.

Los permisos dependen de lo que inició el comando:

- **Tus comandos personalizados, recompensas y eventos** usan la configuración de acceso que elegiste para ellos. El bot no vuelve a verificar los niveles de rol de las funciones; algunas también imponen restricciones de contexto. Elige con cuidado quién puede ejecutar el comando.
- **Las solicitudes al chat de IA** verifican el nivel mínimo de cada función. Si un espectador le pide a la IA que banee a alguien, por ejemplo, recibe un error de permisos a menos que sea moderador. La IA también verifica la configuración de acceso de cualquier comando personalizado que llame.
- **Las referencias a comandos (`#(...)`)** desde tus propios comandos no verifican la configuración de acceso del comando llamado. Solo cuenta el acceso del comando que hace la llamada. Si un comando está abierto a todos y llama a uno solo para moderadores, ese comando de moderadores se ejecuta igual. Ten en cuenta la configuración de acceso de cada comando de la cadena.

## Mensajes de error comunes

| Mensaje | Qué significa | Qué hacer |
|---------|---------------|-----------|
| `[Unknown function: nombre]` | No existe ninguna función con ese nombre | Revisa la ortografía en la [Referencia de funciones AST](/es/commands/advanced/functions/). Los alias como `vip` y `add.vip` funcionan los dos |
| `Usage: $(nombre ...)` o un texto de uso de `$(nombre ...)` | Falta un argumento obligatorio o está mal | Compara tu llamada con la sintaxis de la referencia de funciones |
| `Error: permission denied - 'nombre' requires moderator permissions` | Una solicitud al chat de IA intentó usar una función por encima de su nivel | No hay nada que corregir. El espectador necesita el rol adecuado |
| `[Parse error: …]` seguido de parte de tu texto | El bot no puede leer esa parte del comando, por ejemplo falta un `)` o una `"` | Busca un `$(`, `%(`, `*(` o comillas sin cerrar cerca del texto mostrado |
| `[Loop error: invalid loop syntax]` | La línea `for` de un bucle está mal escrita | Revisa la sintaxis de bucles en [Sintaxis y datos AST](/es/commands/advanced/syntax/) |
| `[Loop error: invalid range loop syntax]` | A un bucle por rango le falta una parte | Usa tres partes: inicio, condición y paso |
| `[Loop error: missing loop body]` o `[Loop error: unclosed loop body]` | El bucle no tiene bloque `{ ... }`, o el bloque no está cerrado | Agrega las llaves |
| `delay: must be between 0 and 60 seconds` | `$(delay)` recibió un número fuera de 0–60 | Usa un valor entre 0 y 60; para esperas más largas, usa `$(timer ...)` |
| `timer: usage: …` | A `$(timer)` le falta el número de segundos o el cuerpo | Agrega ambos: `$(timer segundos "cuerpo")` |
| `timer: could not schedule timer` | No se pudo guardar el timer, por ejemplo por un límite de timers pendientes o un fallo de caché | Espera a que se ejecuten algunos y vuelve a intentar |

## Límites por plan

| Límite | Gratis | Premium | Pro |
|--------|--------|---------|-----|
| Profundidad de bucles anidados | 2 | 3 | 4 |
| Iteraciones de bucle | 25 | 50 | 100 |
| Guardar en variables de base de datos (`%(*nombre ...)`, `%(**nombre ...)`) | No se guarda | Sí | Sí |
| Días temporales de VIP y moderador en funciones AST | Se ignoran los días; el rol permanece | Sí | Sí |
| Funciones de ruleta | Sí | Sí | Sí |

En el plan Gratis, las escrituras en variables de base de datos se omiten sin mensaje de error. El comando sigue ejecutándose, pero el valor no se guarda. Las lecturas siguen funcionando.

En el plan Gratis puedes anidar dos niveles de bucles (un bucle dentro de otro). Premium permite tres, y Pro permite cuatro.

## Límites de referencias a comandos

Una llamada `#(nombreComando argumentos)` ejecuta otro comando personalizado después de la respuesta actual:

- Se pueden anidar hasta **cinco** niveles de referencias.
- Un comando que ya está en la misma ruta de llamadas se detiene. Así, un comando no puede llamarse a sí mismo en un bucle.
- Una sola ejecución puede hacer como máximo **50** referencias en total, sumando todos los niveles.
- La respuesta de cada comando referenciado se publica por separado, después de la respuesta principal.

## Límites de retrasos y timers

- `$(delay N)` pausa el comando hasta **60** segundos. Mientras espera, retiene el resto del comando.
- `$(timer segundos cuerpo)` ejecuta su cuerpo más tarde, de **1** a **604800** segundos (siete días). Devuelve el control de inmediato.
- Cada timer guarda su contenido y su contexto en la caché del bot, así que puede sobrevivir a un reinicio.
- Si el bot estaba apagado cuando llegó la hora de un timer, puede ejecutarse si tiene menos de **10 minutos** de retraso. Al llegar a ese límite, expira.
- Un timer se ejecuta **como máximo una vez**. Un fallo después de reclamarlo puede hacer que se pierda la acción; su ejecución no está garantizada.
- Los timers se pueden anidar hasta **cinco** niveles.
- Un canal puede tener hasta **100** timers en espera al mismo tiempo. También hay un límite compartido de **10.000** timers pendientes y de **64 KiB** por trabajo guardado.

## Lista de revisión para depurar

### 1. Empieza simple

Antes de construir el comando completo, prueba una versión mínima.

```bash
¡Hola $(user)!
```

### 2. Agrega una función a la vez

Un buen orden:

1. texto simple
2. argumentos
3. funciones
4. variables
5. condiciones
6. bucles

### 3. Verifica que el valor exista

Si un valor de caché o de base de datos podría no existir todavía, revísalo primero:

```bash
*(^(#wins) ? %(#wins) : "todavía no hay victorias")
```

### 4. Recuerda que asignar reemplaza el valor

Esto no suma. Pone `#wins` en `1` cada vez:

```bash
%(#wins 1)
```

Para sumar, lee el valor y guarda el resultado:

```bash
%(#wins *(%(#wins) + 1))
```

### 5. Revisa el evento que inicia el comando

Funciones como `$(cheer.amount)` y `$(reward.input)` dependen de los datos del contexto. En una prueba normal pueden devolver vacío, `unknown` o `0`. Eso es lo esperado.

<Aside type="note">
Si una función de evento parece vacía durante una prueba en el chat, normalmente la función no está rota. La prueba simplemente no incluye los datos de ese evento.
</Aside>

## Trampas comunes

### Los valores de caché vencidos aparecen vacíos

Una variable `#` o `##` vence 24 horas después de su última escritura. Un valor vencido se lee como vacío. Usa `*` o `**` para valores que deban durar.

### `&t` debe ir al final

`&t` toma el resto del texto. Después de él no puedes crear un placeholder numerado nuevo, como `&p3`. Si lo intentas, recibes un error.

### `&p1` es una sola palabra

`&p1` es solo la primera palabra. Para un nombre con espacios o una frase, usa `&t`.

### El cuerpo de un timer se ejecuta después

`$(timer ...)` guarda su cuerpo. El mensaje y las acciones que contiene no se ejecutan mientras corre el comando. El timer devuelve el control de inmediato, y cuando llega la hora se publica el mensaje y se ejecutan las acciones. Al llegar a 10 minutos de retraso, expira sin ejecutarse.

### Las referencias a comandos se envían por separado

La respuesta principal se publica primero. Luego las referencias `#(...)` del mismo nivel se ejecutan en orden y publican sus respuestas. Las referencias anidadas de cada comando terminan antes de pasar al siguiente. Si la respuesta principal no se puede publicar, los comandos referenciados se omiten. La respuesta de un comando referenciado no se vuelve a leer como AST.

### Los bucles muchas veces no hacen falta

Si un bucle se puede reemplazar por una sola expresión o una sola referencia a comando, usa la opción más simple.

### Las acciones fuertes en comandos públicos

Configura el acceso del comando según quién deba poder activar sus acciones. Para acciones sensibles como la moderación, considera limitarlo a moderadores de confianza.

## Orden práctico de depuración

Cuando un comando falla, revisa en este orden:

1. ¿Los argumentos son los que espero?
2. ¿Creé la variable antes de leerla?
3. ¿Estoy asignando un valor o sumándolo?
4. ¿Esta función se puede usar aquí, en este plan y con este evento?
5. ¿Creé una cadena de bucles o referencias demasiado profunda o larga?

## Consejo para probar sin riesgo

Primero arma la respuesta y después agrega los efectos secundarios.

Por ejemplo, prueba el texto y las condiciones antes de agregar:

- `$(ban ...)`
- `$(vip ...)`
- `$(set.title ...)`
- `$(start.poll ...)`
- `$(trigger.send ...)`

Así confirmas la lógica antes de que el comando cambie algo en tu canal.

# dima-rust Agent Guide

`dima-rust/` contains a Rust library and native stream-activity and raid-analytics child executables used by dimabot's existing cron supervisor. `scripts/saas-ops build cron` compiles and stages the executables in the cron candidate; it does not add a service or Compose container. Read [`migration-notes/README.md`](../migration-notes/README.md) for migration status and evidence. Read the root [`AGENTS.md`](../AGENTS.md) first; its production-host and scope rules take precedence.

The feature-gated library includes lazy native MongoDB and Redis/Dragonfly client utilities and bounded MongoDB projectors. Stream activity is active in production, with `STREAM_ACTIVITY_RUNTIME=typescript` as its explicit rollback path. Raid analytics reuses the existing raid history, summary, and domain-event collections and was deployed as a Rust child in cron run `cron-b24a505b7fc8` on 2026-10-21; its initial 165-second production acceptance watch passed, with ordinary-load observation continuing. TypeScript remains the explicit rollback path. Read [`migration-notes/README.md`](../migration-notes/README.md) for source contracts, measured evidence, and rollout status; technical stream behavior is in [`STREAM_ACTIVITY.md`](STREAM_ACTIVITY.md). Keep additions within an explicitly requested scope. Do not treat a utility or binary as authorization to connect to production services or migrate existing application behavior. Use isolated, disposable MongoDB data for runtime checks.

## Production-host Rust build and test policy

This checkout is on the production VPS. Before Rust validation, inspect CPU, memory, disk, and production load, and require at least 8 GiB `MemAvailable` outside the configured build allowance: at least 12 GiB before the default 4 GiB cap, or 14 GiB before the conditional 6 GiB cap. Start only one task-owned Docker compiler container across the parent and delegates, with verified cgroup limits `--cpus=4 --memory=4g --memory-swap=4g --pids-limit=256` (`--memory-swap` equal to the memory limit means no swap) and `CARGO_BUILD_JOBS=2`. Apply these limits to dependency builds, build scripts, linkers, and generated test or fixture binaries. Keep `MemAvailable` above 8 GiB during execution and stop if it falls below that floor or production service pressure rises; these are operational thresholds, not a peak-memory forecast or reservation, and CPU/memory caps do not eliminate I/O impact. Use a read-only source snapshot or copy and task-owned Cargo target/cache; do not mount `.env` files or production data, expose the Docker socket, or use host networking. Dependency downloads may need network access, but tests use isolated disposable fixtures only. A 6 GiB cap is allowed only after measured compile need or an OOM under the 4 GiB cap and a fresh headroom check; keep 4 CPUs, do not increase beyond 6 GiB, remove hard caps, or fall back to host execution. `nice`/`ionice` may supplement but do not replace cgroup limits. On a non-production development machine, Cargo may run locally with `CARGO_BUILD_JOBS=1`.

The previous stream-activity validation ran Cargo compilation and Rust test/benchmark binaries directly on the host with `CARGO_BUILD_JOBS=2` and `nice -n 10`; only its MongoDB fixture was in a container limited to 1 CPU and 768 MiB. The Cargo job count and `nice` setting are not hard host limits and do not meet this policy. The `saas-ops build cron` path now compiles in a capped task-owned toolchain container and verifies its applied limits; the deployed cron release was built and validated through this path.

The normal cron build uses only `--no-default-features --features mongo`; Cargo defaults intentionally retain the complete shared foundation (`mongo`, `redis`, `postgres`, `http`). The `postgres` feature is optional SQLx/PostgreSQL support for a possible future telemetry port; current telemetry stays in the TypeScript cron host. `http` is optional Axum support, and `redis` is the optional Dragonfly-compatible client. MongoDB-only workers exclude those three from their dependency graph. Use `scripts/saas-ops build cron --rust-feature-matrix` only for an explicit feature-transition audit. The helper stores dependencies and Cargo artifacts in a private persistent cache at `~/.local/state/saas-ops-rust-cache/v1`, keyed by toolchain image, manifest, lockfile, recipe, features, and profiles. It enforces an 8 GiB cache limit, validates ownership markers, and rejects symlinked paths. Each run explicitly cleans and rebuilds both worker release binaries while retaining dependency artifacts; the optional manual fixture example is not part of routine cron builds. Cache reuse reduces compile work only; it does not imply proportional runtime memory or CPU savings.

## Library conventions

Cargo features keep capabilities independent. The default feature set retains the complete foundation for library/manual consumers: `mongo`, `redis`, `postgres`, and `http`. MongoDB-only workers and their binaries are built with `--no-default-features --features mongo`; SQLx/PostgreSQL, Axum, and Redis are optional and excluded from that worker graph. `dotenvy` is part of the MongoDB feature for explicit environment-file loading. Map BSON documents into explicit structs with Serde, and call Garde `validate()` for additional field or business constraints. Future ports must preserve existing collection names, field types, defaults, and indexes. See [`README.md`](README.md) for the shared MongoDB, Redis, and dotenv foundation.

`dima_rust::utils::mongo::get_mongo_client().await` returns `mongodb::error::Result<&'static Client>`. It reads `MONGO_URI` from the process environment on first use without loading dotenv files, pings `admin` before caching the client in a Tokio `OnceCell`, and leaves failed initialization retryable. Use it within the application's long-lived Tokio runtime and share it across tasks and threads. Static storage does not keep the originating runtime alive; do not reuse the cached client after that runtime or the client has been shut down. Clone the native handle when needed; clones share the same pool. Callers select the database explicitly. The URI's default database may be used through driver behavior, but the utility adds no implicit fallback.

`dima_rust::utils::redis::get_redis_client().await` returns `redis::RedisResult<redis::aio::ConnectionManager>`. It reads `DRAGONFLY_HOST` and `DRAGONFLY_PORT` from the process environment, matching `dimabot/src/utils/databases/dragonfly.database.ts`, without loading dotenv files. It uses plain TCP with database 0 and adds no URI, password, TLS, or database-selection configuration. A Tokio `OnceCell` caches the manager only after the first connection and `PING` succeed; failed or cancelled initialization can be retried. The five-second bound applies to this initial connection and ping. The cached manager is an owned, cheap clone that shares a multiplexed TCP socket. Its response timeout is unset to preserve blocking command semantics; blocking commands and Pub/Sub should use separate dedicated connections when implemented. Use it within the application's long-lived Tokio runtime; static storage does not keep that runtime alive, and the cached manager must not be reused after runtime shutdown. The driver reconnects after an I/O disconnect, while a command that encounters the disconnect is returned to its caller and is not replayed. Configuration errors omit raw environment values. This utility does not load dotenv files; an executable must load explicitly selected files before creating the Tokio runtime.

Run library checks from this directory. On the production VPS, every Cargo command below is subject to the [production-host Rust build and test policy](#production-host-rust-build-and-test-policy); do not run these commands directly on the host:

```sh
cargo fmt --all -- --check
cargo check --locked --all-targets
cargo clippy --locked --all-targets -- -D warnings
cargo build --locked
cargo test --locked
```

Use `cargo run --bin stream_activity -- --help` or `cargo run --bin raid_analytics -- --help` for the manual binaries. Cargo build checks and default Rust tests need no database or cache services; the MongoDB and Redis integration tests use external fixtures and are ignored by default. The stream-activity parity harness and raid migration candidate check are documented in [`STREAM_ACTIVITY.md`](STREAM_ACTIVITY.md), [`migration-notes/README.md`](../migration-notes/README.md), and [`ops/README.md`](../ops/README.md). Run service-backed checks only against isolated, disposable data. Keep `Cargo.lock` tracked and use `--locked` for the documented checks.

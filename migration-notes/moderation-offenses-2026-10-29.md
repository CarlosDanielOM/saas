## Redis behavior and dependency gap

`OffenseStore` can use an injected shared `ConnectionManager`; its default `connect` path obtains the concrete native shared Redis/Dragonfly connection through `get_redis_client`. A nonempty decision ID selects the exact Lua branch: look up a global receipt; if it exists return its numeric value; otherwise increment the offense counter, set its expiry only when the count is one, write the receipt with a separate 86,400-second TTL, and return the count. A malformed existing receipt that makes Lua return nil maps to zero, matching the source's `Number(null)`. Empty or absent decision IDs use separate INCR and EXPIRE calls, with EXPIRE issued only for count one. The counter's fixed window is not refreshed by subsequent offenses. Native code adds no automatic application retry. Redis errors can occur after earlier mutations, and a lost INCR reply can leave an increment without expiry.

The source wrapper calls global `startTelemetry`, wraps selected client operations with spans and GET/HGET hit/miss observations, and installs connection/error event logging with per-caller suppression. In this source utility, `eval` is wrapped; INCR and EXPIRE are not. The native store offers explicit EVAL span telemetry through `with_telemetry`, but the default path does not bootstrap global telemetry/process metrics or connection-event logging. Thus, the concrete connection replacement is verified while a required transitive application runtime adapter remains open; the mapping is partial.

Once a store operation has been polled, the native owned task preserves parent telemetry context and continues through the operation if its awaiting caller is cancelled. This matches the source promise's continued operation. The default acquisition future may still be cancelled before spawning that store operation. No automatic retry is added for ambiguous outcomes.

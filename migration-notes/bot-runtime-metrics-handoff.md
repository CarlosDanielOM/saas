# Bot runtime metrics — slice 7 authoring handoff

Status: **held; authored only, uncompiled and untested**. Local coverage is incomplete, total migration completion is not established, and no caller adoption or deployment has occurred.

Discovery: `bot/index.ts` starts the TypeScript loop; EventSub, message handlers, chat history and roles record runtime counters. Qdrant retrieval emits semantic metrics, and stream-memory worker/runner emit job/action metrics. The thread router emits threading metrics. Existing Rust `observability::Telemetry` writes the distinct `observability:v1:inbox` tracing protocol, so it cannot replace these hash/list contracts. `utils::redis::get_redis_client` already supplies the lazy shared manager; explicitly pass its result to `BotRuntimeMetrics::new` within the same long-lived Tokio runtime. Construction does no network I/O or spawning.

Linux process RSS uses a bounded `/proc/self/status` read and PID/units/overflow checks; process uptime uses `/proc/self/stat` start ticks, `/proc/uptime` and `sysconf(_SC_CLK_TCK)`, rounded in the snapshot as in the source. Unavailable data is null. This follows `cron_supervisor::telemetry::{parse_native_rss,parse_native_stat}` and its 16 KiB bounded read, but that module is gated by the worker's `cron-supervisor` feature and imports the worker registry. Directly depending on it would pull in worker-owned integration; integration should extract the common parsers/reader into a shared module and replace the local implementation when ownership permits. Reads are synchronous procfs reads bounded to 16 KiB, at flush time. Non-Linux platforms lack these adapters.

`start` explicitly owns a 20 ms Tokio timer sampler and the snapshot loop. Its fixed 1 ms buckets cap percentile resolution at a 1000 ms overflow bucket; min/max/mean/stddev retain actual measured lateness. The `tokioSchedulingDelay` field reports timer wakeup lateness with sample count and bucket details. It is **not equivalent** to Node's `monitorEventLoopDelay` histogram, especially on a multithreaded Tokio runtime. It resets with each snapshot. Normal shutdown aborts and awaits the sampler, stops and awaits the loop, then flushes; dropping the handle aborts both tasks without flushing. `shutdown` can wait on Redis and the owner must bound it externally; if cancelling its future, drop the handle as well. One active loop per instance is enforced, not globally across separately constructed instances. Start only within a running Tokio runtime.

Node version, Node heap total/used, external/array-buffer allocation, Node active handles/requests and Node event-loop statistics have no native equivalents here and remain null. RSS and process uptime can be null on unsupported platforms or procfs errors. Existing consumers must tolerate these nulls and separately opt into the Tokio scheduling field. No full runtime or platform parity is claimed.

The adapter authors runtime counters, snapshots/history/cumulative/minute hashes, semantic memory and stream-memory job/action writes. Its Redis methods return errors for the application to log and suppress, matching the source's best-effort intent; the periodic loop suppresses errors. A failure can leave partial writes, and after a snapshot/reset the window is lost on write failure or cancellation. Counter field write order matches the TS declaration order. Typed floating inputs preserve ordinary fractional payload/queue/batch/input character values; fractional hash increments are rejected by Redis after prior commands just as with the source's `HINCRBY`. Empty EventSub string normalizes to `unknown`, other strings remain exact and type writes keep insertion order for ordinary non-index labels. JS object enumeration sorts integer-index labels ahead of other labels; this Rust writer does not, so unusual numeric event names can produce a different command order. Source accepts arbitrary JS values at runtime despite TS types; Rust APIs require typed inputs, and non-finite/overflowing semantic inputs, enormous counters, numeric formatting and malformed/fractional environment settings are not full JS coercion parity. `from_env` is explicit and invalid numeric values fall back to defaults instead of JS NaN; consumers should provide finite representable inputs and valid integer configuration. Semantic methods take explicit Unix milliseconds; `thread_routing` uses team1's own clock.

Contract tl1-c2: `thread_routing` calls team1's `record_thread_routing_metric`, never writes threading keys itself. Team1's router already emits the metric, so integration must not invoke the wrapper again for the same operation. Team1 registration remains a dependency.

# Redis application runtime — 2026-10-29

## Scope

This bounded Rust addition introduces an opt-in owner for application cache initialization and telemetry lifecycle. The accepted code is `8d278890`; its frozen source tree is `48aee6a62657916c8864f12be863214e5af61737dfec4f6fdb4cf950056b7739` (1,353 inputs). The implementation is [`redis_application_runtime.rs`](../dimabot/src/utils/redis_application_runtime.rs), enabled through the `redis-application-runtime` feature and registered in `utils`. It reuses the existing Redis manager, telemetry type, and exporter task. It adds no worker, dependency, default feature, or production startup change.

The application owner tracks `Empty`, `Pending`, `Ready`, and permanently `Closed` states. The first caller starts one detached initialization flight; concurrent callers subscribe to a `watch` result and receive the same manager/telemetry pair or the same error. Dropping a waiting caller does not cancel the leader. A failed attempt returns the owner to `Empty` so a later call can retry. A drop guard clears and notifies a pending flight if initialization is interrupted. Shutdown aborts and joins a pending leader, or shuts down the active telemetry task so it flushes; all later acquisitions fail.

The process-wide wrapper uses `OnceLock`, so its cached `ConnectionManager` must stay within the same long-lived Tokio runtime that initialized it. The existing `get_redis_client` remains the connection provider and keeps its five-second connect-and-`PING` deadline. The runtime adds no pacing while work is ready. The existing ten-second telemetry aggregation interval is retained. The two-second held `PING` and cancellation deadlines are confined to the private test fixture; they do not represent production waiting policy.

`PermitStore::connect` and `OffenseStore::connect` now acquire the shared application manager and attach telemetry when available. Their explicit constructors and existing operation behavior remain available. This instruments those two stores only; other Redis consumers continue using their existing paths.

## Telemetry and compatibility boundary

After successful cache initialization, telemetry starts once only when `DRAGONFLY_HOST` is nonempty and `OBSERVABILITY_DISABLED` is not the literal string `true`. The configured client uses a structured TCP address and defaults the port to 6379. Invalid telemetry configuration silently disables the exporter. The selected service label is inferred from the native executable name (`cron`/worker, `bot`, otherwise `api`), which is a heuristic and does not correctly identify every current native worker name.

This does not reproduce the full TypeScript process observability integration. Runtime RSS, CPU, V8 heap and event-loop measurements, dropped-runtime metrics, connection and error logging/suppression, Redis SDK connection events, and exporter environment refresh are not implemented here. TypeScript derives service identity from `argv[1]` and rereads endpoint environment on exporter reconnect; native code fixes the exporter endpoint at bootstrap. Native telemetry gate changes after first successful initialization have no dedicated test. The runtime identity is not fenced across Tokio runtimes, so callers must preserve the documented single-runtime lifetime.

## Adoption and completeness

This feature remains opt-in. It does not change default application construction, enable a feature in a worker profile, replace all Redis users, or establish caller adoption in the TypeScript application. The native `PermitStore::connect` and `OffenseStore::connect` paths use the shared owner, but the TypeScript application callers remain unadopted. The broader `getDragonflyClient` behavior for other Redis methods and callers remains open, as do runtime RSS/CPU/V8 metrics, logging and suppression, SDK connection events, exporter environment refresh, native service identity, and native telemetry-gate-change coverage. Caller adoption is tracked separately and is not a prerequisite for a 100% dependency-complete port; this bounded result does not establish 100% completion. No source retirement, deployment, push, or performance result is claimed.

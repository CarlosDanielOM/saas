# Permission error limiter handoff

The standalone Rust port and its source-parity verification are complete. See the [2026-10-29 evidence note](permission-error-rate-limit-2026-10-29.md) for the frozen source identity, validation results, isolated-run limits, and cleanup readback.

The TypeScript export `shouldLogPermissionError` is implemented in `dimabot/src/utils/permissions/error_rate_limit.rs`. Its behavior uses only standard-library state and time facilities plus the existing `JsString` compatibility type. The permissions feature already provides the serialization compatibility needed by that type; no Cargo dependency or feature change was needed. The permission module exposes the function, and the utility module enables `JsString` under the existing permissions feature. There is no missing application-specific adapter or external service dependency for this export.

The Rust API offers an independently owned `PermissionErrorLimiter` and a process-wide `should_log_permission_error` singleton. It uses a 300,000 ms default interval, retains at most 2,000 keys, refreshes insertion order only when a call is logged, and evicts the least-recently-logged key. It preserves JavaScript UTF-16 key identity and IEEE-754 timing comparisons, including the source behavior at threshold boundaries. `None` represents omitted/default time and interval arguments. Invalid values introduced through runtime casts outside the declared TypeScript contract (string keys and numeric times/intervals) are not part of the parity claim.

This note covers one exported utility. It does not claim that the wider permissions module, permission handlers, or every caller has migrated. TypeScript roles, moderation, message handling, and the existing barrel/caller paths remain unadopted. No TypeScript retirement, deployment, or push is included or authorized by these verification results. There is no limiter benchmark or measured CPU/RSS improvement; expected constant-time operations and the key-count cap are structural properties, not performance measurements. Arbitrarily long keys mean the key-count cap is not a hard total-byte bound.

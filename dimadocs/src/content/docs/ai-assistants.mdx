Most AI assistants that can open public web pages can read these docs, including GPT, Grok, Gemini, and Kimi. Start with the [documentation index](/llms.txt). Every page also has a **Read Markdown** link at the bottom, which gives the same text, examples, and tables as plain text.

## Files the assistant can read

Each plain-text page includes its original web address, so the assistant can cite it. Prefer single pages for a focused question. The full files are useful when the assistant can read large documents.

## A prompt you can use

```text
Help me create a custom command for DomDimaBot.
Read https://docs.domdimabot.com/llms.txt and follow the relevant links first.
I want: [describe the command and an example chat message].
My plan: [Free, Premium, or Pro].
Who can use it: [everyone, subscribers, moderators, or broadcaster].
Create it through: [Twitch chat or the dashboard].
Explain the response body, setup, expected output, and how to test it.
Cite the pages you used. Ask about missing requirements, and do not invent
functions or use another bot's syntax. If you cannot read a page, tell me.
```

If your assistant cannot browse, open the relevant **Read Markdown** links and paste their content into the conversation.

## Give an answer that can be used

1. Confirm the command's purpose, inputs, who can run it, and the streamer's plan. For a command that stores data, decide whether the data belongs to the channel or to each viewer, and how long it must last.
2. Use a plain text response when that is enough. For dynamic behavior, use DomDimaBot's syntax: `$(...)` calls a function, `%(...)` reads a variable the user created, and `&p1` reads the first argument. Placeholders such as `{user}` do not work here.
3. Give the **command name**, **response body**, **cooldown**, and **user level** separately. For chat setup, also give the full `!cc` instruction. The name passed to `!cc` has no `!`. Viewers type the `!` when they run the saved command.
4. Check each function's arguments, storage lifetime, plan requirement, and limits in the linked references. Set up any stored value before the command reads it. Limit commands that moderate chat or change channel settings to the people who should run them.
5. Describe a normal input and its expected output. For arguments or stored data, also describe what happens when input is missing and on the first run. Label these results as expected. Do not claim a generated command ran unless you tested it.

## Worked example: a welcome command

Goal: let viewers type `!hello` to get a welcome message with their own name.

| Setting | Value |
|---------|-------|
| Name | `hello` |
| Response body | `Hello $(user)! Welcome to the stream.` |
| Cooldown | `10` seconds |
| User level | `everyone` |

As the broadcaster, or another moderator who can create commands, type this in Twitch chat:

```text
!cc -cd=10 -ul=everyone hello Hello $(user)! Welcome to the stream.
```

Or enter the settings above in the dashboard's **Commands** editor. In the response field, save only the response body, not the whole `!cc` line.

When a viewer named `Alex` types `!hello`, the expected reply is:

```text
Hello Alex! Welcome to the stream.
```

This uses the documented [`$(user)` function](/commands/advanced/functions/). It needs no arguments or stored variables. Test it in your channel after you create it. Check that the command is enabled, and wait for the cooldown before you try again. To change an existing command, use `!ec`, as described in the [commands overview](/commands/overview/).

## What these files are

The index and plain-text pages are generated from the same documentation source on every site build, in English and Spanish. They include the original web address for citations, and links that the assistant can follow without running JavaScript or signing in.

Readable docs do not guarantee that an AI provider indexes them, or that every generated answer is correct. Give the assistant the index address directly, ask it to cite the pages it actually read, and test the command before you rely on it.

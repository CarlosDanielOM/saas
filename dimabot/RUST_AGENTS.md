## Migration completeness

100% migration completion means every TypeScript file feature and accepted improvement, plus every required direct and transitive dependency, is implemented in Rust without relying on unmigrated TypeScript. Report local feature coverage separately from total completion, and name any blocking dependency. A trait, mock, or host boundary does not count when the required application-specific adapter is missing; required application services passed through callbacks or traits remain part of the dependency chain. Native Rust crates and standard-library replacements count; npm internals do not need porting. Equivalent Rust types may cover type-only TypeScript imports. Report deployment and caller adoption separately: dependency completeness neither authorizes live cutover nor requires deployment for 100%.

## Production-host Rust build and test policy

### Production isolation for Rust tests

Rust testing is authorized only against isolated, disposable resources. A test request does not authorize a release or deployment; require a separate explicit user instruction before deploying Rust to production. Do not run Rust tests or test code inside production containers, or stop, start, restart, recreate, remove, rename, or reconfigure them. Tests must not use production databases, Dragonfly/Redis caches or queues, credentials, volumes, or networks. Use uniquely named and labeled task-owned containers/networks/volumes and temporary image tags; never overwrite an image tag referenced by a live service. Read-only inspection of container identity and health is allowed to verify isolation, but no production mutation may be presented as a check. Before and after verification, compare production container IDs, image IDs, start times, and relevant mounts/configuration. If any production identity or configuration changes unexpectedly, stop and report; do not attempt repair. Clean up only resources owned by the task; never run Docker prune or remove shared/production resources. Keep the CPU/memory/headroom/no-swap limits below in force.

Testing from this production-host checkout must use the isolated capped Rust compiler workflow and a read-only source snapshot. Never run host Cargo builds/tests or point fixtures at live services. Candidate images for isolated behavior checks must use task-unique tags. The compiler cap does not grant authority to alter a production service or deploy it.

## Library conventions

Cargo features keep capabilities independent. The default feature set retains the complete foundation for library/manual consumers: `mongo`, `redis`, `postgres`, and `http`. MongoDB-only workers and their binaries are built with `--no-default-features --features mongo`; SQLx/PostgreSQL, Axum, and Redis are optional and excluded from that worker graph. `dotenvy` is part of the MongoDB feature for explicit environment-file loading. Map BSON documents into explicit structs with Serde, and call Garde `validate()` for additional field or business constraints. Future ports must preserve existing collection names, field types, defaults, and indexes. See [`RUST.md`](RUST.md) for the shared MongoDB, Redis, and dotenv foundation.

The opt-in service features (`email`, `posthog`, `qdrant`, `s3`, `otel`, `jwt`, `re2-compat`, `socketio`, `audio`) are library foundations for TypeScript util ports, recorded in [`migration-notes/ts-util-foundations.md`](../migration-notes/ts-util-foundations.md). Keep them out of `default` and out of worker profiles unless a worker needs one, and review that profile's dependency guard in [`ops/rust_build.sh`](../ops/rust_build.sh) first. Each disables crate defaults and uses rustls. Network tests use the loopback recorder in `src/utils/test_http.rs` or ignored fixture tests; never point them at production services. Regenerate the RE2 corpus with `node dimabot/tests/fixtures/re2_parity.mjs` when changing `re2_compat`.

`dima_rust::utils::mongo::get_mongo_client().await` returns `mongodb::error::Result<&'static Client>`. It reads `MONGO_URI` from the process environment on first use without loading dotenv files, pings `admin` before caching the client in a Tokio `OnceCell`, and leaves failed initialization retryable. Use it within the application's long-lived Tokio runtime and share it across tasks and threads. Static storage does not keep the originating runtime alive; do not reuse the cached client after that runtime or the client has been shut down. Clone the native handle when needed; clones share the same pool. Callers select the database explicitly. The URI's default database may be used through driver behavior, but the utility adds no implicit fallback.

`dima_rust::utils::redis::get_redis_client().await` returns `redis::RedisResult<redis::aio::ConnectionManager>`. It reads `DRAGONFLY_HOST` and `DRAGONFLY_PORT` from the process environment, matching `dimabot/src/utils/databases/dragonfly.database.ts`, without loading dotenv files. It uses plain TCP with database 0 and adds no URI, password, TLS, or database-selection configuration. A Tokio `OnceCell` caches the manager only after the first connection and `PING` succeed; failed or cancelled initialization can be retried. The five-second bound applies to this initial connection and ping. The cached manager is an owned, cheap clone that shares a multiplexed TCP socket. Its response timeout is unset to preserve blocking command semantics; blocking commands and Pub/Sub should use separate dedicated connections when implemented. Use it within the application's long-lived Tokio runtime; static storage does not keep that runtime alive, and the cached manager must not be reused after runtime shutdown. The driver reconnects after an I/O disconnect, while a command that encounters the disconnect is returned to its caller and is not replayed. Configuration errors omit raw environment values. This utility does not load dotenv files; an executable must load explicitly selected files before creating the Tokio runtime.

Run library checks from this directory. On the production VPS, every Cargo command below is subject to the [production-host Rust build and test policy](#production-host-rust-build-and-test-policy); do not run these commands directly on the host:

```sh
cargo fmt --all -- --check
cargo check --locked --all-targets
cargo clippy --locked --all-targets -- -D warnings
cargo build --locked
cargo test --locked
```

The seven worker binaries and the cron index expose `--help` as documented in their source guides. Cargo build checks and default Rust tests need no database or cache services; MongoDB/Redis integration tests use external fixtures and are ignored by default. Run service-backed checks only against isolated disposable data. Keep `Cargo.lock` tracked and use `--locked` for documented checks. See [`migration-notes/telemetry-counter-release.md`](../migration-notes/telemetry-counter-release.md) for the current run and [`migration-notes/worker-shared-utils.md`](../migration-notes/worker-shared-utils.md) for the historical shared-utility run.

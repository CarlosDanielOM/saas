The sixth native Rust cron responsibility is raid-session retention, late-follow capture, and moderation-request admission. It reuses existing MongoDB collections and Redis follow-defense state through the shared native clients. Its cron binary uses the existing `--no-default-features --features mongo,redis` profile. It adds no HTTP provider, collection, index, schema, configuration key, or service. Existing TypeScript session producers, APIs, and shared raid utilities remain active. The TypeScript `follow-defense-actions` worker continues to execute Twitch bans; Rust admission durably hands work to that existing action path and makes no Twitch calls.

## Operations and bounds

Each tick runs three operations in order:

1. **Retention:** extend one eligible retained session to 72 hours, then set its purge time to 73 hours after the session start. Extend follower purge times before advertising the longer session retention so followers are not removed first.
2. **Journal backfill and late attribution:** read at most 200 existing `domain_events` rows from the session's bounded backfill window, in ObjectId cursor order. Rows with a non-document payload or missing/falsy user field are deliberately skipped, and the cursor advances across them after a successful batch. A read, write, or processing failure aborts before cursor advancement so the batch can be replayed. Attribute newly delivered follows to the correct raid session, update capture bounds, and apply any currently valid future-follower eligibility from the existing Redis follow-defense state.
3. **Moderation request admission:** claim and fence one eligible request with a 60-second lease, process at most 200 followers, and enqueue durable idempotent action records before marking followers as queued. Recheck cancellation controls and protection settings before admission. Completion updates are fenced by the lease token; ordinary errors leave incomplete followers available for retry. SIGTERM/SIGINT stops after the current bounded tick. The hard 20-second initialization/tick watchdog exits nonzero and retains durable cursors and the request lease for recovery. Bounded work remains fair: each backfill and admission operation handles at most 200 rows, preserving existing request deadlines and the separate TypeScript action-executor pacing.

The executable is `raid_sessions`. It supports `--help`, `--dry-run`, `--once`, `--telemetry-json`, `--database NAME`, and repeatable explicit `--env-file PATH`. It does not load `.env` automatically; inherited environment values take precedence over explicitly selected files. Scheduling is outcome-based: continue immediately when a backfill or admission batch is full at 200 or other ready work remains; wait one second only when the worker is idle, has only future work, or the tick failed. This intentionally changes the archived TypeScript loop, which paused one second after every tick. It preserves bounded batches, fairness, request deadlines, and the existing TypeScript action-executor pacing; no performance benefit is claimed without measurements. The supervisor reads the `raid_sessions:` stdout protocol, exports under metric prefix `raid_sessions_rust`, and records the bounded batch metric as `batch_items`; failed ordinary ticks report zero processed items and retry after one second. A hard OS-level watchdog exit is nonzero by design and emits no batch frame; it logs the exact diagnostic `Raid session active work exceeded 20-second watchdog; durable work retained for recovery` and leaves the durable cursor and request lease for recovery. Initialization failures may also exit nonzero before a batch frame.

# Expressive TTS tag types — 2026-10-29

## Scope and implementation

This follow-up gives the existing expressive-tag configuration a closed native type surface. `ExpressiveTtsTag` has a private checked index, accepts only exact canonical names through parsing and `FromStr`, exposes `as_str`, and iterates in the existing 75-tag catalog order. The implementation reuses the current catalog groups; it does not define a second tag-name list.

`ExpressiveTtsTagSettings` stores one boolean per catalog tag in a private fixed-size array. It supports construction from a filled value, catalog-order construction, an all-true default, typed get/set, and ordered iteration. JSON conversion consumes the cached `ExpressiveTagConfig` directly rather than projecting it through a `BTreeMap`; ordered serialization uses the existing `write_json_utf8` writer. This preserves the source record's tag order for callers using the typed record.

The existing map-based APIs remain available as semantic convenience APIs and retain their lexical map iteration behavior. They are not replaced by the typed record. No filter, reinforcement, or settings-normalization algorithm changed. There are no dependency, Cargo manifest/lock, default, or worker-profile changes, and no caller adopts the new types in this follow-up. The local closed-tag, complete-record, ordered-JSON, and runtime metadata contract is now covered; broader source-retirement audit and caller inventory remain open.

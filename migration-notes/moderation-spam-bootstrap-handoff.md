# Spam bootstrap and response-loss test handoff

The opt-in `moderation-spam` integration test `moderation_spam_bootstrap` requires fresh, exclusive task-owned MongoDB and Dragonfly fixtures. It guards the exact `keyword-mongo:27017` and `keyword-redis:6379` endpoints, `DIMA_RUST_TEST_RESOURCE_OWNER=dimabot-migration`, a unique `KEYWORD_FIXTURE_NAMESPACE`, and `DIMA_SPAM_PRIVATE_FIXTURE_OWNER` equal to that namespace. Run serially with the existing spam storage tests: the global budget key is deliberately the real, unnamespaced application key. The fixture owner must tear down the private servers after failures.

The parent test starts separate online and offline child processes to isolate the application's cached Redis owner. The offline case uses port 1 and checks both acquisition errors and the absence of Mongo chatter and Redis budget/marker writes. The online case checks the actual marker and budget writes and shared `CLIENT ID`. The response-loss case preloads the exact spam Lua script, drops its successful response after execution, and asserts a surfaced error, one command, one increment per budget, and TTLs. A second proxy drops a successful SET response following the real Mongo upsert; command monitoring checks one update, and a subsequent caller sees the cache marker without another update. Both proxies forward only to the guarded private Redis alias. The prior variation-jobs test re-exports the extracted proxy unchanged in its default mode.

These checks ran in the parent's capped isolated fixture workflow. Functional phase `compiler-fixtures-1793339134095509298` passed the native online/offline child bootstrap checks, actual EVAL reply-loss check, actual SET reply-loss-after-Mongo-upsert check, telemetry success/error sampling, cache lookup hit/miss aggregation, two private Mongo/Dragonfly storage checks, and all 38 existing variation-job scenarios. It also reached all 37 async source records; nine of those are explicitly synthetic boundary adapters, not native wire replays. The borrowed-view final phase `compiler-fixtures-1793340894915777003` also passed the updated source replay, private storage/bootstrap and response-loss paths, and strict feature checks on the frozen 1,424-input tree. The response-loss checks used task-owned private Redis/Mongo services and proxies constrained to the guarded private Redis alias. The EVAL reply was dropped after the script executed, with a single command and one increment per quota plus TTLs. The SET reply was dropped only after the real Mongo upsert; command monitoring observed one update, and the following caller observed the cache marker without repeating it. Preserve the failed overall status when summarizing these passed subchecks.

The original duplicate-key fixture passed `11000` without the structured error details expected by the pinned Mongo driver. The fixture now supplies `keyPattern` and `keyValue`, as required by MongoDB's duplicate-key error construction; this corrects the synthetic server response and does not change application behavior. MongoDB's [`commands.cpp`](https://github.com/mongodb/mongo/blob/master/src/mongo/db/commands.cpp) reads optional `errorExtraInfo` when constructing the injected failure, and [`duplicate_key_error_info.cpp`](https://raw.githubusercontent.com/mongodb/mongo/master/src/mongo/db/storage/duplicate_key_error_info.cpp) parses the structured `keyPattern` and `keyValue` fields. The upstream [`failCommand` failpoint guide](https://github.com/mongodb/mongo/wiki/The-failCommand-fail-point) documents `enableTestCommands` and application-name scoping used by the isolated test.

The explicit telemetry test records sampled GET, SET, and EVAL success and error spans, plus cache lookup hit and miss aggregates. Telemetry output uses a separate loopback endpoint. The existing source acquisition mock records remain mock evidence; the child tests independently exercise concrete application acquisition paths. No deployment or TypeScript caller adoption is implied.

The [v1 wire contract](../dimabot/DESKTOP_AI_CONTRACT.md) describes the API behavior.

## Source and reuse

The OAuth API derives owner, channel, and broadcaster authority from the authenticated desktop session. Bot and Pet turns use `ai:interact` and `pet:interact`; discovery requires `profile:read`, and `/desktop-ai` activity requires `desktop:connect`. Fresh consent can create eight-scope sessions with either interaction scope or nine with both; existing seven-scope sessions remain unchanged.

The implementation adds durable turn/conversation records and HTTP admission, read, cancel, speech-event, and ticketed audio routes under `dimabot/src/desktop_ai/`. It reuses the shared chat/action pipeline, existing memory, tools and credit rules, broadcaster action identity, Pet `talk` admission/queue, and existing TTS provider, voice and billing services. Bot audio uses private HTTP delivery and the shared output coordinator rather than the normal public TTS queue. Pet uses its existing elected player. Neither path adds local PC command execution or a parallel AI, Pet, or TTS system. Turn records support seven-day idempotency; the desktop thread context window is 24 hours, while normal shared memory policies remain in effect.

The desktop owner flow auto-submits the final transcript after wake detection for the selected Bot or Pet conversation/command. There is no additional Send gate, parser, or bouncer. Microphone capture is gated across Bot, Pet, normal TTS, and browser output. Bot cancellation does not count as silence proof: for started playback, only a matching initiating-session `ended`/`failed` event or the bounded playback deadline releases the output gate. For Pet and normal TTS stop, durable retired-output proof is tied to the elected peer/socket, previous lease, and execution deadline; a legacy desktop `stopped`/`error` report is not trusted without the same-session stop monitor guarantee.

## DIMA-050: opt-in turn status hints

**Status:** Server source commit `97c63c8c` was built and verified on exact candidate run `api-ab6e37aa7052`, image `sha256:4676e943506a189891b16b9ce07bef2df0186017317275cee0b4f090013067da`. The API was deployed and started at `2026-11-04T05:30:37.491215544Z`; exact-image restart count is zero. Startup readiness passed with no fatal, unhandled, or uncaught errors. The desktop app manager retains separate client acceptance and hardware verification; no desktop client release, tag, or push is claimed. Helper cleanup completed with rollback artifacts retained; no task-owned test containers, networks, or copied provider fixtures remain.

This additive API work reuses durable desktop turn receipts and their shared snapshot revision domain, the authenticated `/desktop-ai` activity namespace, and existing Pet owner-scoped Redis wakeups. The new `turn-status-v1` feature is opt-in; clients without it retain the legacy activity event surface. Turn updates carry only receipt identifiers and a safe-integer revision as invalidation metadata. Receivers re-fetch authorized snapshots; hints do not replay work or convey transcript or playback data. Publication is post-commit and best effort. Pet metadata enrichment uses two shared bounded queries for 64 recent links, with per-peer deduplication capped at 128 revisions; delivery rechecks session, user, client, channel, and scopes. This avoids per-client polling. The contract is in [DESKTOP_AI_CONTRACT.md](../dimabot/DESKTOP_AI_CONTRACT.md), and isolated check setup is in the [desktop AI fixture guide](../ops/checks/desktop-ai-fixtures/README.md).

The capabilities GET advertises `features: ["turn-status-v1"]`. Clients that require hints must inspect this field; against an older server or a response without that feature, they retain the existing authorized HTTP polling path and do not depend on hint delivery.

The Bot audio ticket, `start_before`, and Redis TTL are 20 seconds from readiness; the existing 90-second preparation reservation and five-minute LLM deadline are unchanged. Playback keeps its separate duration-plus-five-second deadline. Review also tightened stale recovery so a started playback cannot be expired by the earlier `start_before` deadline.

The final candidate passed 22 exact-image runtime groups and 354 compiled tests across 34 suites, with zero failures or skips. The checks covered legacy and opt-in capability discovery, session and scope authorization, stale in-flight GET, new-ready hints, polling fallback, Pet revision matching, 16-second audio fetch, 20-second expiry, one-fetch plus started proof, replay prevention, and existing output fencing.
